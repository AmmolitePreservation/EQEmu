# GUID worklist

The work for Live-style item GUIDs ([README.md](README.md) has what Live does and the design). Statuses: `fix` (write code, SQL or docs; the content is given), `liveCheck` (observe Live), `peridotTest` (run on peridotguids), `question` (the owner decides), `polish` (after the first pass works), `done` (kept for the record).

**Counts.** fix 18, liveCheck 0, peridotTest 6, question 0, polish 4, done 13; 41 in all.

## Owner decisions

- **GUIDs first (2026-10-25):** the work is GUIDs and PlayerHousing, equal peers, GUIDs first: this branch (`guids`, from `main`'s tip 6fedcae84) with its own migration, tested on peridotguids (a new clone of Peridot); housing on `housing` is paused until `guids` is merged into `housing` and migrated, then reworked on top (its REC-16 to REC-18, DOC-39).
- **Live dictates.** Everything Live shows is copied exactly, the server stamp included; EQEmu's own structures are kept where they serve (side tables keyed by GUID, snapshots, the session serial).
- **Build order and one migration (2026-10-27):** the remaining schema work cannot be built or tested one table at a time (dropping a side table's copied columns loses data until MIG-1 has moved the rows, and nothing can move rows until the item layer and inventory live in `item_instances`), so the order is ISS-1, SCH-4, SCH-3, SCH-5, SCH-6, MIG-1, then the tests; every commit builds, and a new character exercises issuing and inventory on an unmigrated peridotguids while existing characters wait for MIG-1. Everything after 9327 is one migration version, 9328: the C++ data move runs at world boot (EQEmu's old "Checking Database Conversions" hook) before the manifest applies 9328's ALTERs and DROPs, gated on the pre-migration schema so a rerun is a no-op and a drop can never precede the move.
- **Every decision in README.md's "The design"** was made with the owner on 2026-10-24/25: the format and world rule, the item table and its derived counter, side tables with foreign keys, the receiver rule and the single issuing path, the quest API, stacks and use, the nine retirement reasons and `World:RecoverableItemStates`, the session serial, the encoders, snapshots with skip-and-log plus `reissue`, and the migration's holder counter plus Live's server stamp.

## Schema (SCH)

- **SCH-1** `done` **The item table.** `item_instances` in migration 9326, as README.md's "The item table" describes it: keyed by the three raw words; item columns; per-holder location or parent and index, one or the other by CHECK; unique held locations over generated columns that free a retired row's slot; retirement state and time; a `BEFORE DELETE` trigger that refuses deletes and `REPLACE`; `ItemInstancesRepository` by hand (no delete or replace, the counter as `NextCounter`), on the generator's ignore list; in `GetPlayerTables` for dumps. Checked on peridotguids' MariaDB 10.5.4 as the `eqemu` user in a scratch database: 21 cases (accepted rows, each CHECK, the unique holds, the parent key, delete and replace refused, the counter's key-only read); the repository compiles with the server's flags. Nothing calls it yet; ISS-1 is its first caller.
- **SCH-2** `done` **The world column and rule.** Migration 9327 adds `character_data.origin_world_id` (the character's origin world, not the one it is on) (`SMALLINT UNSIGNED`, default 0); `World:WorldID` (default 0) gives it; `Database::SaveCharacterCreate` stamps it and refuses a rule value outside 0 to 65535 with an error, and `StoreCharacter` now honors that refusal. The base repository carries the generator's `world_id` lines (the generator run against Peridot's database also swaps `ingame` and `first_login`, which Peridot's table holds in the other order; that swap is not taken). Tested on peridotguids through the client: with the rule at 7, Kolobe (120) was created with world 7 and kept it through the zone's whole-row save at camp; at 70000, Yoyay was refused with the logged error (EQEmu's own failure path soft-deleted its reserved name row, 121); the rule is back at 0. The player record and the issuing path read the column in ENC-1 and ISS-1; existing characters are stamped in MIG-1.
- **SCH-3** `fix` **Side tables keyed by GUID.** `trader`, `character_parcels`, `guild_bank`, `character_evolving_items` and a ground-drop table move to GUID keys with foreign keys and drop their copied item columns; `object` keeps static content only. A ground row's holder id is the zone (SCH-1), so the ground-drop table should not repeat it; it holds the instance, position and heading, and the zone-boot retirement of stranded `ground` rows (ISS-3) joins it by instance. Gaps ISS-1 left for this item, where a side table still copies item columns: a stackable guild bank withdrawal and a guild bank stack's charges (the row is not updated), a Bazaar sale completed from world (`worldserver.cpp` retires the seller's row `sold` and the buyer's copy is issued anew), the Bazaar inspect and buy lookups (SEC-1), and `character_evolving_items` matched by item number at load.
- **SCH-4** `done` **Absorbed tables dropped.** `inventory`, `sharedbank`, `character_corpse_items`, `bot_inventories`, `character_pet_inventory`, `character_parcels_containers`, `object_contents`, after their rows move to the item table; every load and save path that read them reads the item table. Done in ISS-1: no code reads or writes `inventory`, `sharedbank`, `character_corpse_items` or `object_contents` any more (character select, zone entry, corpses and world containers read rows). Left: the 9328 migration drops them after MIG-1's move; `bot_inventories` (a bot's load and save still use it; the layer moves rows in and out of the `bot` holder meanwhile, so a returned bot item with augments gets its augments reissued until this is done), `character_pet_inventory` (ISS-6), `character_parcels_containers` (a parcel's contents are already children of the parcel row; the table is still written at send and dropped here), `DeleteCharacter` and `CopyCharacter` through the layer. Second pass (2026-10-29): bots load and save rows at the `bot` holder (`BotDatabase::LoadItems`, `SaveItemBySlot` with the owner as issuer, `DeleteItems` retiring `botDonated`, colors by row update, `CreateCloneBotInventory` through `ItemLayer::CopyRows`, starting items issued through the layer); pets with ISS-6; parcel contents come from the parcel row (`character_parcels_containers` no longer written or read); `Database::DeleteCharacter` retires everything the character held as `characterDeleted` (`RetireCharacterItems`) and `CopyCharacter` copies the held rows as new items from the copy's counter; `PurgeCharacterParcels` retires pruned parcels `expired`. ## Issuing and lifecycle (ISS)

- **ISS-1** `done` **One issuing path.** `ItemLayer` (common/item_layer) issues, moves, updates, retires and loads; README.md's "How the layer is reached" says where it is called: the receiver's landing funnel, not the creation sites. Built with it in one unit (the first commit that writes `item_instances` must also read it): the inventory, cursor, bank, shared bank and trade slots load and save from rows (`SharedDatabase::GetInventory`, `SaveInventory(client, slot)`, `SaveCursor`, `SaveSwap`); starting items are issued at creation from the new character's first counters; corpses hold rows (`MoveItemRowsToCorpse` at death, `LootItemFor` from rows at load, loot moves rows back, `Corpse::Delete` retires `decayed`); dropped items move to `ground` when the object is made and retire `decayed` at its decay; world container contents are rows (`LoadWorldContainer`, `SaveWorldContainer`, a combine retires them `consumed`); trades move rows in one transaction; hand-ins retire `consumed` when the NPC keeps the item; a pet's take moves the row to `pet` by its equipment slot; parcels move rows to `parcel` and back; a guild bank deposit moves the row and a whole-item withdrawal brings it back; a bot's take moves the row and its return brings it back; a Bazaar sale carries the seller's GUID or issues the sold piece from the seller. Tested on peridotguids with a new character (Acjure, 122): nine starting items issued {122, 0, 0..8}; a swap through the cursor; a split (counter 9) destroyed; a summoned stack (10) merged and retired `stacked`; a note into a bag (parent 8, index 0) and the bag moved as one row; death at level 60 moved every row to corpse 475 and loot-all moved them back; camp and relogin rebuilt the inventory from rows. Left to later items: `Database::DeleteCharacter` and `CopyCharacter` walk `DatabaseSchema::GetCharacterTables`, which cannot name `item_instances`; both go through the layer in SCH-4 (hard delete retires `characterDeleted`, a copy issues new GUIDs). The RoF2 client refused to drop an item on the ground through claudelink's click in the tutorial zone, so the ground path is tested in TST-1; a trade needs two clients at once, also TST-1.
- **ISS-2** `done` **Stacks and use.** With ISS-1: a split piece is a fresh instance (or a clone with `ClearGUID`) issued at landing; a merge updates the destination and retires the piece `stacked` (`MoveItemCharges`, `SwapItem`, trades); `DeleteItemInInventory` with a quantity saves the smaller stack or retires the last unit with the caller's reason; a partial sale or destroy is a split by the client first.
- **ISS-3** `fix` **Retirement reasons.** destroyed, sold, stacked, consumed, expired, decayed, characterDeleted, removedByGM, rolledBack, petDonated, botDonated, set at every point an item leaves play (destroy, sell, merge, combine, hand-in, task delivery, charges, no-rent and temporary expiry, corpse rot, ground despawn, hard character delete, GM removal, rollback). Done with ISS-1 for every `DeleteItemInInventory` caller (129 sites classified: client destroys and duplicate-lore removals `destroyed`, merchant sales `sold`, merges `stacked`, consumption, combines, hand-ins, tributes and every script removal `consumed`, no-rent lapses `expired`, corpse deletion and ground decay `decayed`, `#nukeitem` and `#emptyinventory` `removedByGM`), with one open question: the five server-enforced removals in `SwapItem` (the shared-bank duplication check and the NoDrop hack check) use `removedByGM` though no GM acted; the owner decides whether a twelfth reason, `removedByServer`, is wanted. Still to do: `rolledBack` (SNP-1). `characterDeleted`, `petDonated` and `botDonated` came with SCH-4 and ISS-6. The five server-enforced removals in `SwapItem` no longer destroy anything (owner, 2026-10-29): a stale shared-bank copy is dropped from the zone's memory and the move refused, since the row is live in another zone, and a NoDrop trade request from a modified client is refused with a kick; `removedByGM` is for GM commands only and no twelfth reason is needed. A dropped item lives only in the zone's memory (`Client::DropItem` makes a `Temporary` object with a five-minute decay and never writes `object`), so its row says holder `ground` with the zone while it lies there (done in ISS-1) and retires `decayed` when the decay fires (done), and, since a zone that dies loses it without a word, each zone retires any row still marked `ground` in that zone as `decayed` when it boots: that needs the ground-drop table's instance column to tell one instance of a zone from another, so it is built with SCH-3.
- **ISS-4** `fix` **No all-zero item.** An item instance without a GUID is a server error; things that aren't items yet are sent as zeros.
- **ISS-5** `fix` **Moves are written through, exchanges are transactions, counter collisions retry.** Done in ISS-1 for moves (every save is one write), for trades, swaps, deaths and Bazaar purchases (one transaction each; `DBcore` transactions nest) and for the counter retry (`ItemLayer::Issue`, three attempts on a PRIMARY collision); parcel retrieval with a bag's contents and the remaining exchanges follow with their holders. Every move writes the item's row at once, as EQEmu writes `inventory` today (one `SaveInventory` per slot change); a move between holders is one `UPDATE` of the row's location, never a delete and insert, which is what makes one item, one place hold. An exchange that moves several rows together (a trade, a Bazaar buy with its coin, a parcel retrieve with a bag's contents, a merge) runs in one database transaction, so a crash mid-way leaves either the old state or the new. The issuing path's insert at `ItemInstancesRepository::NextCounter` retries a key collision (MySQL error 1062 from `InsertOne`) up to three times, then fails loudly; the collision is logged with the character and the two counters.
- **ISS-6** `done` **Items a pet or bot takes out of play retire with their own reasons.** A pet's items (holder type pet, written when the pet is given them and kept while it is suspended, as `character_pet_inventory` does today) retire as `petDonated` when the pet dies, is dismissed or depops: EQEmu makes no corpse for an owned NPC (`!HasOwner()` in `NPC::Death`), as Live makes none. A bot's items stay held through its death; deleting the bot retires them as `botDonated`. Both reasons may be listed in `World:RecoverableItemStates` (Live has no bots; the default list stays `destroyed,decayed`). Mercenaries hold no item instances in RoF2 (no mercenary inventory traffic; EQEmu's `merc_inventory` is a content template), so there is nothing to stamp or retire for them. Built with SCH-4's second pass: a handed-over item's row moves to `pet` by the equipment slot the pet's loot entry took (`NPC::AdoptPetItem`); at zone-in or recall the pet's loot entries take their rows' GUIDs (`AdoptPetItemRows`); suspending moves rows to `suspended_pet` and recall moves them back; death (`NPC::Death` for a client's pet), `/pet get lost`, a suspension or recall without equipment, and a character save that finds no pet (or no suspended pet) retire `petDonated`; `LoadPetInfo` fills the pet's item numbers from rows and `SavePetInfo` writes no items. A bot's deletion retires `botDonated`; ammo a bot uses up and an item a bot consumes retire `consumed`.

## Trust (SEC)

- **SEC-1** `fix` **A client-sent GUID is a selector, never an authority.** The server decides whose items a packet may name from the session, and the GUID only picks one item within that scope. One scoped lookup in the item layer, `lookup(scope, guid)`, serves every handler; no handler runs a bare lookup by GUID on the item table. The scopes: the character's own held items (inventory, bank, cursor, their trader listings, their parcels); the current listings of the trader a Bazaar request names (buy and inspect, as Live allows); the character's own retired items (the Recovery tab). A GUID outside the scope, an all-zero or placeholder GUID (`{0, 0, n}`, what the client gives a locally split stack), or text that fails the round-trip decode is refused and logged at Warning with the character, the GUID and the scope tried; what follows is the server owner's call. Every update, move, listing, sale, destruction or recovery follows only from a scoped lookup, so one expressed against an item the character does not hold cannot be written. The paths on this branch: Bazaar buy and inspect, trader price update, evolving XP transfer, parcels, the Recovery tab.

## Migration (MIG)

- **MIG-1** `fix` **Its own migration, version 9328.** Every existing item and augment gets a row in a fixed order (table, then row key): character-held items take their holder's counter (bots their owner, parcels their recipient); the shared bank, the guild bank, ground drops and world-container contents take Live's server stamp, generated exactly as 0x80c890, with the process id and start time recorded so a rerun reproduces every GUID. Every character is stamped with the world rule; #4460's serials are discarded.
- **MIG-2** `fix` **Pre-GUID inventory snapshots are cleared.** They name items by slot and item number and map to no row, so the migration recreates `inventory_snapshots` in the GUID shape, empty, and says so in its notes; Peridot has none (the feature is off there), so nothing is lost. ## Snapshots and recovery (SNP)

- **SNP-1** `fix` **Restore by GUID.** Held items move back and take their snapshot values; retired items come back; `stacked` pieces only with their stack; items acquired since retire `rolledBack`; items held by others are skipped and logged (GUID, item, holder).
- **SNP-2** `fix` **`#invsnapshot restore <timestamp> reissue`.** Skipped items are recreated with new GUIDs from the restored character's counter; the log pairs old and new.
- **SNP-3** `fix` **`World:RecoverableItemStates`.** The rule (default `destroyed,decayed`), loud on an unknown name, refusing `stacked`. The Recovery tab itself (merchant tab, recovered rows keeping their GUID) is built with it.
