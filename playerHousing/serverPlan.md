# Server Implementation Plan

**Phase 2** of the server work (phase 1: `serverWork.md`): each foundation and subsystem planned against Peridot's EQEmu source (`PhoenixCampfire/peridot`, upstream `ab45d4358`, v23.8.1). Written in chunks. `codeReconciliation.md` maps the code against this plan (what stays, changes and is written new) and gives the build order; the client research and Live's behavior remain the specification.

**Principle: surgical.** Housing lives in its own module; existing EQEmu code is touched only at the points listed below, each for a stated reason. New tables, a few altered fields and data rows are expected.

**Scope:** the standard housing system (`serverWork.md`) **and all three non-standard extensions** (X1 private zones as interiors, X2 custom neighborhood maps, X3 plots in the live world; section below), designed together.

**Development model:** everything is designed first, then written in full, and the owner builds once. **Database work is tested for real** before delivery: migrations and queries run in a sandbox MariaDB created from the server's real schema (`pok-schema-all.json`), including the `items` rename and decode against the exported rows. **Code is verified by careful reading** against Peridot's source and the research specifications; EQEmu isn't built in the sandbox. After the owner's build, validation happens in game with the diagnostics plugin and the Lua harness.

**Status:** the design is complete and is built in `codeReconciliation.md`'s order: step 1, the schema and generators, is done and tested; trophies (S12) are the last step, outside the first build. The chunks after chunk 1, each covering the standard system and X1-X3 together:

## Chunk 1: architecture

### How housing reaches the client

- **Client messages** arrive in `Client` through the opcode table `ConnectedOpcodes[]`, filled by `MapOpcodes()` (`zone/client_packet.cpp:90`); entries are `Client` member functions (`ClientPacketProc`). Emu opcodes are named in `common/emu_oplist.h` and mapped to RoF2 wire values by `utils/patches/patch_RoF2.conf`.
- **Server messages need no translation layer.** Every opcode's encoder and decoder default to `PassEncoder` / `PassDecoder` (`common/struct_strategy.cpp:17-18`): a packet with no registered encoder goes out as built, only its opcode translated. Housing exists only for RoF2 clients, so **the housing module builds RoF2 wire formats itself** and never touches `rof2.cpp`'s message encoders or `rof2_structs.h`, except where T6 lists.
- **Zone-in** completes in `Client::CompleteConnect()` (`zone/client_packet.cpp:531`): the F5 send sequence starts there, its records before `OP_WorldObjectsSent`, so the zone-entry line names the property as Live's does (chunk 4).

### Module

New code in **`zone/housing/`**, one file per concern: the manager (per-zone state and the zone-in sequence), wire builders (RoF2 formats from the research), handlers per subsystem, rule checks (the client's rules, reproduced server-side), and persistence through repositories. Handlers dispatch internally on the emu opcode.

### Persistence

- **Housing tables** follow EQEmu's repository pattern: generated base repositories (`utils/scripts/generators/repository-generator.pl`, the same generator as the 250 existing ones) plus thin extended repositories for queries the module needs.

- Schema design (tables and fields for definitions, zone templates, cost elements, properties, balances, placed items, access lists, regions, polls, trophies) is part of chunk 3, where each table's shape comes straight from its messages.

## Chunk 1: decisions

**D1. Where the housing tail's item values live. Decided: rename `items` columns in place and fix their data.**

The PEQ-derived `items` table already holds the housing tail, captured from Live in unlabeled columns: **`UNK224`-`UNK241` (with `placeable` at 235) are the 18 captured housing-tail fields, in the client's memory order** (proved field by field on rows captured aligned; the values match the client's semantics: bitmask 8 on houses, 128 on guild halls; house definition ids 5-34, guild halls 38-41, the crate 31; upkeep ids 17-24). Most rows were captured **shifted by one byte**: on the wire `bInteractiveObject` follows the housepet string, and that capture didn't know it, so from the trophy id on each column holds the next field's bytes one position early (and `UNK233`'s low byte is the interactive flag); a few rows were captured aligned. **`UNK223` is not part of this and is left untouched:** on the wire the client reads `Placeable` immediately after the `Heirloom` byte, so no tail field sits between them (the capture's field numbering isn't wire order), and it isn't a copy of EQEmu's `subtype` either (they differ on 2,710 of 117,944 items).

| Column | Becomes | Client field |
|---|---|---|
| `UNK224` | `placeable` | the "placeable in" bitmask (`+0x5ac`) |
| `UNK225` | `placeable_ignore_collisions` | `+0x5b0` |
| `UNK226` | `placement_type` | `+0x5b4` |
| `UNK227` | `real_estate_definition_id` | `+0x5b8` |
| `UNK228`, `UNK229` | `placeable_scale_min`, `placeable_scale_max` (float) | `+0x5bc`, `+0x5c0` |
| `UNK230` | `real_estate_upkeep_id` | `+0x5c4` |
| `UNK231` | `max_per_real_estate` | `+0x5c8` |
| `UNK232` | `housepet_file_name` (string) | `+0x5cc` |
| `UNK233` | `trophy_benefit_id` (-1 = none) | `+0x5ec` |
| `UNK234` | `disable_placement_rotation` | `+0x5f0` |
| `placeable` | `disable_free_placement` | `+0x5f1` (EQEmu's 2015 migration named `UNK235` `placeable`; it isn't) |
| `UNK236` | `npc_respawn_interval` | `+0x5f4` |
| `UNK237`-`UNK240` | `placeable_default_scale`, `_heading`, `_pitch`, `_roll` (float) | `+0x5f8`-`+0x604` |
| `UNK241` | `interactive_object` | `+0x608` |

- **Why rename rather than add:** EQEmu's server never reads these columns (the shared-memory loader's `item_fieldlist.h` skips the block) and EQEmu itself renamed unknowns in place before (migration 9093); renaming keeps one source of truth, no second "placeable", and the column count (dumps keyed by position still load).
- **Cost, accepted by the owner:** Spire's item model maps these columns by name, so **Spire's item editor, item endpoints and eqtraders item import break** for them. Spire's server control doesn't use the item model (its dashboard only counts items), so it keeps working.
- **The migration** (`sql/itemHousingTail.sql`, generated by `tools/makeItemHousingTailSql.py`) keeps the raw capture in **`items_housing_capture`**, decodes from it (aligned or shifted, detected per row), retypes the 18 columns in place and renames them in one atomic `ALTER`, so every column keeps its position. **Non-placeable items** get max per real estate -1, trophy id -1 and zeros: the full table has only three non-placeable patterns (83,732 never captured, 23,977 shifted, 4,658 aligned), and the captured ones already decode to exactly those values. **Guards** (named check constraints) stop it before any change if a placeable row has no single plausible layout, a housepet capture isn't empty, or a non-placeable row is outside those patterns. It runs while `UNK224` exists (check `SHOW COLUMNS FROM items LIKE 'UNK224'`, condition `not_empty`), and every statement before the final `ALTER` can be repeated.
- **Tested** (`tools/testItemHousingTail.py`, MariaDB in strict mode, the real `items` definition and the exported rows): every value matches the decoder bit for bit, the column order is unchanged, a re-run after stopping mid-way gives the same result, and each guard stops it cleanly.
- **The decoder is validated** (`tools/itemTailDecode.py`) against all **5,577** items with a placeable bitmask: **every row has exactly one plausible layout** (5,205 shifted, 372 aligned; none ambiguous, none implausible both ways), and every decoded field is sane: trophy ids decode to exactly the trophy items (100 "Idol of Severilous", 111-120 the "Empowered Trophy of ..." series, 121 "Trophy of Expanding Life"; 88 in all, the rest -1); default headings and pitches fall on EverQuest's 512-unit scale (0, 128, 256, 384); respawn intervals 4500 (familiar NPC items), 750 (NPC merchants) or 0; default scales 0.25-5.0; scale ranges 0.05-25; disable free placement on 170 items (houses, halls), disable rotation on 455; **exactly one interactive object, the Guild Regeneration Pool**. **Shifted rule** (per 32-bit value, little-endian): `UNK233`'s low byte is the interactive flag; each field from the trophy id on is the high three bytes of its column plus the low byte of the next (`UNK233`/`UNK234` form the trophy id; `placeable` is the rotation flag; `UNK236`'s low byte is the free-placement flag). **One oddity kept as captured:** the Candy Dish (55446) has bitmask -1 (placeable anywhere).
- **Live's current values replace the capture's where they differ** (owner's decisions, from Live's item definitions; 2,519 items are in both): **the placeable bitmask on 485 items**, every change widening where the item goes: 446 gained guild yards (14 to 142), 17 Decorative Dummies gained houses (2 to 6), 16 mounts and familiars gained guild halls and yards (12 to 142), 4 Action Goblins gained guild halls (4 to 6), the Winter Juniper Tree everywhere (8 to 142) and the Decorative Augmentation Sealer houses and yards (130 to 142); **the minimum scale on 56 weapons**, 0.5 to 0.1 (Sceptre of Destruction, Bronze Halberd and the like, so they shrink to décor size); **the default orientation of 46 items**, so they're placed upright (35 paintings and the like rolled a half turn, 7 a quarter turn, three of which also turned a quarter in heading, 0 to 128: Painting: Tahka Estarim, Painting: Balebri Estarim and the Impromptu Body Protector; 3 tiles rolled three quarters, and the Hovering Contraption's pitch 128 to 0 with its rotation unlocked). These are the item definitions' own fields, the same on every copy: a copy's placement keeps its own transform (15 copies of Tile - Shadow share roll 384 in their definition, placed at many orientations); **no per-property limit on the four Action Goblins**, 1 to -1 (Live's usual; 102 items keep a limit of one); and **the housepet model names**, Live's for the 134 NPC items it showed, while each other NPC item takes the name of the NPC it spawns (chunk 5: the client only checks that the name isn't empty). **A migration of their own applies them** (version 4, `sql/itemHousingAdoption.sql`, generated by `tools/makeItemHousingAdoptionSql.py` from Live's item definitions), after the decoding one.
- **Content found along the way:** Live's real-estate catalog ids: house definitions 5-34 (by style, size and interior), guild halls 38-41, the moving crate 31; upkeep cost ids 17-24 for houses by size.
- **Reaching the serializer:** the in-memory item (`ItemData`) still doesn't carry these fields, so the housing module loads them for items with a non-zero `placeable` and the RoF2 serializer asks it through the provider hook (T6); items without them serialize as today.

**D2. Cross-zone updates. Decided: first-class, fully implemented** (owner's decision). Zones and instances are separate processes; the client hears only from the zone it's in, so anything that changes in one process and matters to a player in another needs a server-to-server message.

**Delivery** follows EQEmu's existing cross-zone pattern (the quest system's `ServerOP_CZ*`): world forwards the op to every zone (`ZSList::Instance()->SendPacket`, `world/zoneserver.cpp`), and each zone filters locally for its targets. Housing adds **one server op, `ServerOP_Housing`**, carrying an envelope:

| Field | Meaning |
|---|---|
| event | which housing event (catalog below) |
| target kind, target id | character (character id), guild (guild id), property (the zones hosting it: its neighborhood's copy and its interior's copy, while they run), zone instance, or all zones |
| origin zone, instance | the sender, for replies |
| property id, revision | the property the event is about, and its revision after the change |
| payload | event-specific data, when needed |

**Events say what changed, not the new data.** A receiving zone re-reads the database and sends its own clients the updates (records, lists, access lists, item lists, world objects). The database stays the single source of truth, and events can arrive in any order.

| Event | Target | Receiving zone does |
|---|---|---|
| Property changed (owner, balances, upkeep, name, children; its payload names the owner and guild before and after) | the property; the owner and previous owner | re-sends the records (`0x63fd`, `0x6fd0` for a current property, `0x4f09` for one that is gone), the property lists `0x2aa7` / `0x3e00` / `0x66df` and the access lists of the players who know it; world's neighborhood balance (D11) runs when the owner or guild changed |
| Item list changed | the property | re-sends the changed entries and world objects |
| Access list changed | the property | re-sends `0x485d`; applies the new permissions to players present |
| Personal trophy benefits changed | the owner | recomputes the available benefits (they come from trophies placed in the owner's plots) |
| Guild neighborhood created | the guild | `0x1d3c` |
| Polls changed | all zones | re-sends the affected poll messages to players with the vote windows' data |
| Catalog changed (a kept `#realestate` edit, `reload`) | all zones | reloads the catalog and re-sends it, and the state that depends on it, to everyone present |

A transfer offer needs no event: the recipient is in the owner's zone, which holds the offer (S7). The expiry lines go from world to an online owner as an ordinary chat message, and the notice mail straight into the `mail` table (S8).

**Consistency:** every change runs inside a database **transaction** (`TransactionBegin` / `Commit` / `Rollback`, `common/dbcore.h`), and each property carries a **revision** checked and incremented by every change (`UPDATE ... WHERE id = ? AND revision = ?`). When two zones change the same property at once, the second change fails cleanly, and that player gets a result code and the fresh state. A transfer offer waits in the owner's zone, where its recipient is (S7), with its expiry, and its answer is checked against the property's revision, so it can't be accepted twice.

**Touch points added:** T11 `common/servertalk.h` (the op and the envelope), T12 `world/zoneserver.cpp` (one `case` in the forward-to-all-zones list), T13 `zone/worldserver.cpp` (one `case` handing the envelope to the housing module).

**D3. House interiors. Decided: plain instances on Live's copy lifecycle** (Q2, settled by Live). An interior is an ordinary zone to the client (it needs the S1-S4 data there too). Live keeps no instance per property: entering a property with no running copy starts a fresh copy of the template its definition's `dz_id` names, everyone permitted shares it while anyone is inside, and it is discarded about 31-33 minutes after it empties, the next entry getting a new id; placed items belong to the property. Peridot does the same with plain EQEmu instances, not dynamic zones (Live's housing shows none of their semantics): **`real_estate_zone_templates`** maps each `dz_id` to its zone, version and zone-in point; on an entry with no running copy, housing takes `GetUnusedInstanceID` and inserts the `instance_list` row (`never_expires` 1, `is_global` 0: both set would reroute instance 0 to it), keeping property to instance only in **`real_estate_instances`**, a row per running copy (the zones are separate processes, so the map is shared through the database; the property's row lock orders entries racing from several zones), and it adds the player (`AddClientToInstance`) before `MovePC`. **The housing zones' own `shutdowndelay`** (32 minutes, `tools/makeHousingZonesSql.py`) keeps an empty copy for Live's delay; at its shutdown housing deletes the instance and its `instance_list` row and clears the map (T27), and world sweeps housing instances with no running zone. Removing an `instance_list_player` row moves nobody, so housing moves occupants out itself on a revoked Enter, a pickup or a swap. A copy holds an instance id only while it runs (32,000 less 100 reserved, shared with expeditions; RoF2's field is u16), and running out fails loudly. A character who logs in to a discarded copy gets a new copy of the same property, where it was saved (the discard records it in `character_real_estate_interiors`, world's login reads it; where Live puts it is INT-22). Neighborhoods use the same path (S6). **New copies count up as Live's do** (INT-14), from `real_estate_instance_counter`, skipping ids in use and wrapping above the reserved ones; world starts the counter over at boot, as Live's numbers suggest (INT-16 confirms or flips that on 2026-10-21). World sweeps a copy whose zone has been down five minutes (a crash; a normal discard is the zone's own). Each zone instance knows what it runs: a copy its `real_estate_instances` property, instance 0 its zone root (X3); the hosted properties are that root's tree, an interior's only the house or hall itself. Q11 (the interior-zone crash) is in testing.

**D4. Upkeep. Decided: a per-property clock run by the world server, on the model of parcel pruning.** World's main loop runs every 32 ms, and its periodic jobs are `Timer` objects whose `Check()` is only a clock comparison (`world/main.cpp`): the instance purge every 450 s, and **`parcel_prune_timer` once a day**, which is gated by rules (`Parcel:EnablePruning`, `Parcel:ParcelPruneDelay`), tells the zones (`ServerOP_ParcelPrune` to every booted zone) and does its database work. The upkeep component follows it: a `Timer` in the loop calls a small world-side housing routine that charges only the properties whose **`next_upkeep_at`** has come (indexed; a pass with nothing due is one query), inside transactions, and sends the housing "property changed" event for each change; **it also runs once at startup**, so upkeep that came due while the server was down is caught up. **Each property keeps its own clock, as on Live** (charges 10.8 to 13.2 hours apart, mean 12.3, on no global or neighborhood schedule): each charge sets the next one `Housing:UpkeepIntervalSeconds` later, give or take up to `Housing:UpkeepJitterSeconds`. The charging rules themselves are chunk 6.

## Configuration: EQEmu rules

**Every housing behavior an operator might tune is an EQEmu rule**, in a new **`Housing`** rule category, the way parcels and merchants are configured (`common/ruletypes.h`: `RULE_CATEGORY(Parcel)` with `RULE_BOOL`, `RULE_INT` and `RULE_REAL`, each with a default and a description). **No SQL is needed for rules**: world injects every declared rule missing from `rule_values` at boot (`RuleManager::UpdateInjectedRules`, `world/world_boot.cpp:318`) and removes orphaned ones. Rule names follow EQEmu's PascalCase.

**The rules**, with their defaults (Live's behavior where known, otherwise the recommended policy; the decisions they carry are D4 and D6-D10). Permission masks use bit *n* for permission *n* (chunk 6).

| Rule | Type | Default | Meaning |
|---|---|---|---|
| `Housing:EnableHousing` | bool | true | master switch: when off, a zone sends RoF2 clients only the empty `0x49df` (chunk 4) and refuses housing requests with a result code |
| `Housing:EnableUpkeep` | bool | true | the upkeep clock (D4) |
| `Housing:UpkeepIntervalSeconds` | int | 43200 | seconds from one of a property's charges to its next (Live: 10.8 to 13.2 hours apart, mean 12.3) |
| `Housing:UpkeepJitterSeconds` | int | 4320 | each interval is longer or shorter by up to this, at random (D4); 0 or more and below the interval, or world does not start |
| `Housing:UpkeepPercent` | int | 100 | percent of every daily upkeep charged, read from the host zone's ruleset (X3) |
| `Housing:UnpaidUpkeepEvictionDays` | int | 90 | days after a charge found a plot's escrow empty (player or guild plot) before world reclaims it into a Crate of Eviction (D7; Live: 90); 0 = never |
| `Housing:SellRefundPercent` | int | 0 | percent of the purchase price refunded on a sale (D6); only 0 is supported, since no column records the price paid, and another value refuses every sale with an error |

## Non-standard housing

Three extensions the owner wants, all in scope: **private zones as house and guild-hall interiors** (a house door leading to your own Plane of Hate or Qeynos; the owner's priority), **custom neighborhood maps** (East Commons as a neighborhood), and **plots in the live world** (plots in the public East Commons).

**What the client allows** (verified):
- **Nothing in the client is tied to the housing zones.** No real-estate code reads `OP_NewZone`, and nothing checks for the housing zone ids (`robustness.md`): plots exist wherever the server sends regions (volumes placed anywhere by a matrix) and property records.
- **What an item may be placed in is decided by the property's type, not the zone.** The placement rule "allowed in this real estate" (`0x5b4d10`) requires the item's placeable bit **`1 << (definition type - 1)`**: Regular Zone `0x01`, Guild Hall `0x02`, Player House `0x04`, Plot `0x08` (yards), Neighborhood `0x10`, Town `0x20`, Guild Plot `0x80` (guild yards); only a Moving Crate (`0x7f61b0`: category 6) accepts any placeable item.
- **So non-standard housing reuses the standard property types.** Live's item data carries the Regular Zone bit on two items only, the Candy Dish and the String of Bones (both -1, placeable anywhere), so a "Regular Zone" property would accept almost nothing; a private zone is a **Player House** or **Guild Hall** property (most furniture carries both bits: 14 and 142), and a plot anywhere is a **Plot** or **Guild Plot**.

**What EQEmu provides** (the schema): spawns, doors, objects, ground spawns, traps and zone points are keyed by **zone version** (`spawn2`, `doors`, `object`, `ground_spawns`, `traps`, `zone_points` all have `version`), `zone` has a row per version with its own `ruleset`, and instances carry a version and `never_expires` (`instance_list`). A private copy of a zone is **an instance of a housing version of that zone**, which has no spawns, doors or zone lines unless content adds them.

| Extension | Design | Additive or binary | Rules and tuning |
|---|---|---|---|
| **X1. **Architecture consequences, adopted now** (cheap now, expensive later):
1. **A property's host is derived, never stored** (NBH-8): its root's definition names the zone (`dz_id`), a zone root runs at instance 0 and any other root in its running copy (`real_estate_instances`); cross-zone "property" events (D2) go to every zone, and each acts on the properties it holds.
2. **Definitions name their zones by `dz_id`**: every definition that can be a zone's current property (a house or guild hall's interior, X1; a neighborhood's template, X2; an X3 root's public zone, at version 0) has a `dz_id`, and `real_estate_zone_templates` maps it to the zone, version and zone-in point. Plots, guild plots and crates have none.
3. **Plot authoring is a first-class tool**: an in-game GM command that defines a plot's region box (position, size, heading) and its definition on any map, used by all three extensions and by standard neighborhoods alike.
4. **Housing rules are read in the zone's context**, so a zone's `ruleset` can tune housing per zone (X3).

**To verify:** that placed objects render outside the housing zones (house exteriors and furniture use global models, but it needs a test; the diagnostics plugin shows it directly: a world object whose actor stays 0 has no body); plot authoring accuracy against the client's own containment (the plugin recomputes it); zone-in traffic in a busy public zone (X3).

## Chunk 2: the item tail (F1)

**Wire layout** (client reader `0x7f6bf0`; `windows/RealEstateItemsWnd.md`): after `Heirloom`, the 18 housing fields in wire order with a **NUL-terminated housepet string** and **`bInteractiveObject` right after it**, a u8 count at `+0x609` (that many u32s follow into `+0x60c`; 0 here), then the reader's last 9 bytes (`+0x110`-`+0x118`); what follows belongs to the caller.

**Today** `SerializeItem` (`common/patches/rof2.cpp:6850-6892`) fills `ItemQuaternaryBodyStruct` and writes it as one block; the client reads its `unknown28` / `unknown29` as a 3-character housepet name `"\xff\xff\xff"`, which absorbs the struct's 6 extra bytes, and `unknown30` (-1) as the trophy id.

**The change** (T6), for every packet type except `ItemPacketInvalid`:
1. write the struct's bytes up to and including `Heirloom` (`offsetof(ItemQuaternaryBodyStruct, Placeable)` bytes), unchanged;
2. write the 18 tail fields in wire order from the item's housing tail (the housepet name as a C string, at most 31 characters), then the `+0x609` byte (0);
3. write the struct's **last 14 bytes unchanged** (from `unknown37`'s second byte to the end: `+0x110`-`+0x118` for this reader, then 5 bytes the caller reads), so everything after the tail stays byte-identical.

**`ItemPacketInvalid` keeps today's bytes** (it sets `unknown29` to `0xff`, which changes how the client reads the name); nothing housing sends uses it.

**The housing tail's values** come from a provider the serializer calls with the item id: a function the zone's housing module registers at boot in every zone, housing on or off (the only item-side hook; a failed load stops the zone's boot), returning the renamed `items` columns for items with a non-zero `placeable`, and for every other item the values the client reads today apart from the name: all zero but max per real estate and the trophy id, both -1, and an empty name. `common/` holds only the provider's plumbing (a struct of the 18 fields, the provider pointer with its setter and getter, and the defaults), so world, which never registers one, keeps sending defaults.

## Chunk 2: the opcode map (F2)

Every housing message, **77 opcode values** (the register's sections 2 and 3, `serverWork.md` and the robustness review's handler list, reconciled). **Three reuse EQEmu's existing names as they are**: `OP_ClickObjectAction` (`0x0c1e`, a housing container closed), `OP_FindPersonRequest` (`0x5cea`, Locate and plot finding) and `OP_OpenContainer` (`0x06c8`, the client confirming any container it opened, a housing container included); `OP_TradeSkillCombine` and `OP_GuildUpdate` (rank permissions, action 5) are reused by name. **The other 74 are housing's own**: one `N(OP_...)` each in `common/emu_oplist.h` (T1) and one line each in `utils/patches/patch_RoF2.conf` (T2), none clashing with an existing name. Each client-direction one maps to the forwarding handler `Client::Handle_OP_Housing` (T3); server-direction opcodes are only sent. **The trophy opcodes are registered with the trophies**, the build's last step; until then the client's trophy messages arrive unhandled and are logged as such.

**Not housing, excluded:** `0x0ecb` (the respawn window), `0x65c7` and `0xcadf` (movement reports), `0x4936` (an item sync), `0x2c4e`, and `0x796c` (Plot Search's alternate branch, unreachable in this build). **`0x89` is not an opcode:** it's the game dialog the transfer offer is shown in; the offer and its answer travel in `0x5a63`. **Three door messages EQEmu doesn't map are added beside these** (OPC-9): `0x7b22` appends one door, `0x51df` adds, updates or removes one door, `0x6d20` sets a door's switch value, so a door changes mid-session without resending every door (X3 dormancy, GM authoring).

**Constraints for what the client can't check:** definition type 1-8, item caps (non-real-estate items within max items; NPC items -1 or within max items), an area id only on plots and guild plots, a name segment only on interiors and crates, an exit point exactly on plots and guild plots, region ids below the property id floor, region volume, zone template zones and headings, access groups 0-6, personal slots 0-9, guild slots 0-3, poll kinds, selection types and dates.

**Migrations** (custom track, T7, generated from the tested SQL by `tools/makeHousingManifest.py`): version 1, the item tail (chunk 2); version 2, the 12 catalog tables (content database); version 3, the 17 state tables; version 4, Live's item housing values (chunk 1, D1). **Until the one build is deployed, a schema change edits these migrations in place** (no new versions), **and nothing is applied to Peridot's database piecemeal**: the code and its database are finished first (owner's rule). **Repositories:** 22, generated by EQEmu's own generator (`utils/scripts/generators/repository-generator.pl`; run it as `perl -X` on Perl 5.38 and later, whose smartmatch deprecation its fatal warnings otherwise die on, silently), none for balances or NPC item actions (read in SQL). **EQEmu's schema lists** (T26) name every table: catalog as content, state as player, and the two per-character trophy tables in the character map, so EQEmu's dumps, character deletion and copy include them.

**Findings from the full-table queries** (they shape later chunks):
- **The trophy benefits aren't in `tributes`**: it holds personal tribute 0-59 and guild tribute 60-82, none of the ids trophy items name (100, 111-121, 201-206, ...). They're content to add (`tributes`, `tribute_levels`). - **Only zone 712 (Sunrise Hills) exists in `zone`**: the house interiors and guild halls need zone rows (chunk 7).
- **House definitions are keyed by size and interior, six exterior styles each** (House 5, 7, 8; Hut 9-11; Residence 12-14; Domicile 15-17; the Cobbler and Behroe sets 18-29; Manor 32-34), so **the definition decides the interior zone**, as X1 needs; guild halls 38-41; the Crate of Eviction 31; **eleven storage crates 174-184**.
- **`guild_permissions`** holds a value per permission (24, 25 and 29: 224; 27 and 28: 128, one guild): its rank encoding is settled with purchase in chunk 6.
- **The character's property lists are named by MacroQuest** (`OwnedRealEstates`, `OwnedItemRealEstates`, `ArchivedRealEstates`): archived properties are a subset of the owned ones, and list B is properties contained in items the character carries (here, by the property id the item carries in its custom data).
- **Live's item display names the property an item carries:** a Monel Style Brick Manor placed at 107 Terminus Street reads "This item contains real estate The Templar Village II, 107 Terminus Street, Three Room House, which has 0 items inside of it." (string 5289, `%1` the neighborhood, the plot's address and the house's name, whether the property's or its definition's; 5288 is the form without a known property) and "This item is placeable in yards." The binary item reader (`ItemClient::CreateItemClient`, `0x5559a0`, calls the item's vtable slot `+0x10`, `0x5553b0`, over a `CUnSerializeBuffer`) reads the header's tail after the two ornamentation strings as: `ornamentIcon` → `OrnamentationIcon` (`+0x84`); EQEmu's `unknowna1` → `ArmorType` (`+0xf0`); `ornamentHeroModel` → `NewArmorID` (`+0x48`); `unknown063` → `Tint` (`+0x138`); `Copied` → `+0x1c`; **`unknowna4` → `RealEstateID`**; `unknowna5` → `RespawnTime` (`+0x78`). **The RoF2 serializer now sends it** (the field renamed `real_estate_id`): the property the item's custom data names (`real_estate_property_id`, parsed by `common/housingPropertyItem.h`, shared with the zone), -1 otherwise. **The Print Items button is Live's later addition:** neither the RoF2 client's string table nor its binary holds it, and its item display has no such control, so nothing is needed.

## Chunk 4: catalog, properties, regions, item lists, zone-in, plot authoring

**Wire primitives** (every housing stream): little-endian integers; **`string` = `u32` length + raw bytes** (records, entries, the catalog); the exceptions are `0x1967` (a raw NUL-terminated name) and the item tail's housepet name (chunk 2).

**S1, the catalog (`OP_RealEstateDefinitions`, `0x2698`):** every definition in wire order (id, `area_id`, `cost_definition_id` and `upkeep_definition_id`, `max_items` and `max_non_real_estate_items`, `max_children` (the effective value, D14), `zone_id` (Live's, 0 on Live) and `dz_id`, type, `placement_group_id`, `address`, `icon`, `max_npc_items` (signed: -1 is no cap), the layout origin y first (`switch_y`, `switch_x`, `switch_z`), `switch_heading`, child count and ids from `real_estate_definition_children`), then every cost element (options in `position` order, each with its items). The catalog is small, so **the whole catalog is sent** at zone-in and again after a GM change.

**S2, properties:** a record per property, **every one sent as `0x63fd`**, which inserts a property the client doesn't know and merges into one it does (`0x6fd0` sets the current property; `0x4f09` makes the client remove a property, so it goes out only for one that is gone): id, `+0x18` (Live's `staticId`: -1, or 0 on a vacant player plot), parent, definition, guild (-1 for none), 0 (fellowship: Live sends the owner's, and EQEmu has none), **the owner's account id as text** (`+0x30`, Live's `primaryHandle`, a per-account handle: Clerictrader and Anastrianaa, on one account, share 633393165 while Pariator's account has 562595939; empty with no owner), **the owner's name** (from `character_data`), 0 (`+0x34`; RoF2 reads neither `+0x18` nor the handle, and these are Live's values, owner's decision), the children's count, **the property name, composed when sent**: its parent's composed name, then a plot's address or the definition's `name_segment` ("Dogwood Bridge Estates, 103 Market Street, Three Room House"; only a neighborhood's own name is stored), the children's ids (from `parent_id`), the balances (`u8` count, then currency and amount as f64), **the upkeep option**, **`upkeep_expired_time`** (`+0x40`: 0 while paid, otherwise the second a charge found the escrow empty), the voting opt-out. The character's lists: A = owned, C = owned and archived, B = contained in an item the character carries: **the item names the property in its custom data** (`real_estate_property_id`), and the property's `contained_in_item` flag says it's there. **Not the inventory guid: EQEmu reassigns every item's serial number (saved as `inventory.guid`) at each load**, so a guid link breaks the first time its carrier zones.

**S3, regions (`OP_RealEstateRegions`, `0x49df`):** `u32` count, then per region its id, the 16 floats (row 0 first) and five zero `u32`s. **The matrix comes from the region's box** (`tools/regionMatrix.py`, tested on 40,000 points): the client tests the player's `LastCollision` **in the order Y, X, Z**, through the inverted matrix, against [-1, 1]; in that order the rows are the across axis `half_x * (-sin, cos, 0)`, the along axis `half_y * (cos, sin, 0)`, `(0, 0, half_z)` and the center `(y, x, z)`, with the heading in EQ units (512 per turn; heading 0 faces +y, EQEmu's own convention). **Region ids stay below 100,000, where property ids start:** RoF2 keeps the placement codes of regions and of the current property in one map keyed by id. **A region belongs to a property through its definition, in the context of the current property**, so every neighborhood instance shares its plot definitions and regions, the neighborhood property being each instance's context. **Interiors need no regions:** with none, "standing in" falls back to the current property, so a house (or an X1 private zone) sent as the current property takes every placement inside it.

**S4, item lists (`0x1cef`, updates `0x087f` / `0x2cf7` / `0x1097`, removals `0x1baf` / `0x1967`, drop `0x7d28`):** each entry: property id, record id (the row id), placed flag, **the item's upkeep expiry** (Live's `upkeepExpiredTime`: 0 while paid, otherwise when its upkeep lapsed, set by the upkeep lifecycle in chunk 6; RoF2 doesn't read it), the transform (heading, pitch, roll, scale, then the position y first), the owner's name, **the owner's account id** as text (Live's `ownerHandle`, the same per-account handle as the record's `+0x34`), then **the item serialized exactly as `OP_ItemPacket` carries it after its packet type**, through the exported RoF2 serializer (T6) from the row's item instance with **the row's GUID**: one per `real_estate_items` row, derived from its id (a hex letter and 15 hex digits, never equal to an EQEmu serial) and the same in every message about the item (world objects, the begin placement, the spawn binding, menus), since RoF2 matches world objects, the Items window and spawns by GUID and EQEmu gives an instance a new serial at every load.

**The zone-in sequence (F5, from `Client::CompleteConnect`, T4)**, in dependency order; **steps 1-4 go out before `OP_WorldObjectsSent`**, so the client's zone-entry line names the property as Live's does ("You have entered Dogwood Bridge Estates, 103 Market Street, Three Room House."), and the rest after it. **In a zone with housing off, with no catalog, or under a dormant X3 root, a RoF2 client gets only step 6's empty `0x49df`**, which clears the regions it remembers from an earlier zone, as Live's zones do:
1. the catalog;
2. **pending crates**: an archived crate the character owns and no item carries (an eviction, or a sale without room) becomes a crate item in a free inventory slot, and so moves from list C to list B; without room it stays archived and the character is told;
3. property records (`0x63fd`) for **the properties hosted here** (this zone and instance), **the character's properties** (lists A and B) and, for each, **its ancestors and descendants** (the context lookup and the personal trophy walk need the trees);
4. the current property (`0x6fd0`): the host's root (a neighborhood, or an X3 zone's root) where properties are hosted; **the house or hall inside its interior's copy**;
5. the character's lists A, B and C;
6. **the regions** of the hosted plots, and an empty `0x49df` in every other zone, which clears any the client remembers;
7. item lists for the hosted properties and the character's properties (personal trophies are computed from the owned plots' items wherever the character is);
8. access lists for the same properties;
9. **world objects** (`0x1045`) for the placed ordinary items of the properties hosted here, and **NPC items** as spawns carrying their binding in the spawn itself (T28), with no world object;
10. polls (chunk 7); trophy slots and timers come with the trophies.

**Across zoning** RoF2 keeps records, definitions and costs, access lists, the owned lists and regions, and resets the current property, item lists, placement, doors and world objects (ZIN-3), so each zone-in sends everything again and the empty `0x49df` clears stale regions. Whether Live's client clears records at a zone change is open (REC-13).

**Plot authoring and administration (T17: one registration in `zone/command.cpp` / `command.h`; the implementation is `zone/housing/housingCommand.cpp`):** a `#realestate` GM command for the content the tables need, without SQL:
- `info`: the properties and regions where the GM stands (the client's containment), with owner, definition, balances, upkeep and children;
- `region create <across> <along> [name] | move <id> | size <id> <across> <along> | show`: a box at the GM's position and heading, 350 below the feet to 350 above (Live's plot regions), its id below 100,000;
- `definition show <id> | set <id> <field> <value> | origin <id> | create <id> <type> <name> | child add|remove <parent> <child>` (fields by their column names; `max_npc_items` takes -1), and `cost set` for any cost, any non-zero amount in coin or an alternate currency, a negative amount a reduction;
- **every edit runs in a transaction and is validated by loading the resulting catalog before it is kept**: one that would break the catalog is rolled back with the loader's reasons, so a typo never switches housing off; a kept one reaches every zone through the **catalog changed** event (D2), as `reload` does;
- later chunks add their own: `village create` (taking the neighborhood definition), `neighborhood balance` and `neighborhood remove` (chunk 6: S6, D11; the one way anything is deleted), `poll` (chunk 7, S11). Random neighborhoods and X3 roots are made by world (D11, D12), not by the command.

Its status level is an account status like EQEmu's other content commands; `Housing:EnableHousing` gates it with the rest.

## Chunk 5: placement, editing and the world layer (S5)

**A placement session** (per client, in memory; dropped on zone-out and disconnect, T5, kept across property refreshes): new or edit, the source (an inventory location, or a property and record), the item's GUID, the context property, the tilts the placement began with (for the rotation lock), and the server's side of the client's request latch: a commit is accepted only for the GUID of the begin it answers. The Augmentater's mode (step 6) joins it.

**Requests and the rules the server replays** (the client doesn't re-check a commit):
- **`0x626e` place request** (60 bytes: the common header with the GUID, property and record ids, the item location and the click's screen X / Y): pick the rule set by source: **from inventory, the client's 13 rules in order** (House of Thule `0x2f`; Veil of Alaris under a guild plot `0x52`; membership `0x53`; plot upkeep current `0x18`; `4`; placeable `0x24`; **the item doesn't go into the property it carries or one of its descendants** `0x1e`; **allowed in this real estate** `0x11`: the item carries the bit `1 << (type - 1)`, any item for a crate; house and guild-hall counts per yard `0x0f` / `0x44` (**the yard's children that aren't crates, against its effective house limit**, `0x5b48b0` / `0x7f5100`: the value the catalog sends, the definition's `max_children` replaced by `Housing:MaxHousesOverride` or raised by `Housing:MaxHousesAdditive`, D14, so the client's check and the server's agree; the item's type picks the code); moving-crate rules `0x27` / `0x51` / `0x20`; **capacity** `0x0a` / `0x0c` / `0x26` from the definition's caps, **waived by a stack merge**; empty containers `0x13`; item and house upkeep `0x19`; **permissions** `0x4b` / `0x4d` / `0x47`; and the item rules the client states: **removing a NO DROP item needs its owner, the placer** (`0x40`), **removing a LORE item is refused while the taker holds one** (`0x41`), and adding needs only the add permission), **from storage** the stored-item set, **between properties** the move set; then, with the trophies (the build's last step), **the trophy rule** (a trophy under the player's guild plot needs rank permission 29, `0x46`); until then trophy items place as ordinary items. A refusal is `0x1228` with the code.
- **The reply, `0x626e` begin placement:** the placement object (below; **a new placement starts at the item's defaults**: its default scale and heading, and the two wall-mount tilts, held-item turn included, as its pitch and roll, as Live's placements begin: 77% of Live objects with non-zero tilts still sit exactly at them, Anastrianaa's two epics on her yard's ground among them, only their heading turned), the location, A = 1 when editing a placed item, B = 1 (preview), C = 0, D / E = the request's click position, F = the NPC item's spawn id when editing one, then **the permission map: a code per region in the context and the extra final pair `{current property id, code}`**, each computed by the same rules for this player and item, **0 where placing is allowed**. The client's green / red preview then matches the server's judgment.
- **`0x711a` commit:** the rules again, for the property the item lands in: the region containing **the item's position**, otherwise the current property (the server has no model data, so it checks the position, not the client's box of 8 corners), plus the scale within the item's range and the item's locks (no pitch or roll off its defaults while rotation is disabled, no free placement while that is disabled); **inside an interior nothing bounds the position**, as on Live (owner's decision). Then, in a transaction with the property's revision: a **new** placement moves the item instance from inventory into `real_estate_items` (charges, augments and all) or **merges into a stack** (same owner, same item, room; rule 10b); an **edit** updates the transform. Then `0x1228`, the entry (`0x2cf7`), the world object (`0x1045`) to everyone in the host zone and instance, or for an NPC item its spawn instead, and the item-list event (D2).
- **The request is refused, with no begin, when the item may not go where the player stands** (the client's `+0x94`: the plot whose region holds the player, otherwise the current property), with that property's code, since the client lets several codes through without re-checking (`windows/RealEstateItemsWnd.md`). **Where the client's rule is not traced the server is stricter rather than looser:** the move set also checks *allowed in this real estate*, the house limits, the crate rules and both upkeeps; a stored or moved item needs Move Item (10), a house also Remove House and Add House; rule 5 (`0x57bfb0`, code 4) and the membership rule (3, EQEmu has none) are not replayed (PLC-19). **A stack merges** only into a stored entry of the same placer and item that has room for the whole stack moved (PLC-18). The per-item limit (`0x1f`, `max_per_real_estate`) is the server's own rule after the client's.
- **`0x2036` pick up** (removal permission, inventory space, and **at most one non-empty house and one non-empty crate in inventory**, `0x21`) and **`0x3424` store** (destination 2 closet, 3 shed, 6 crate, resolved to the property's own storage; the client's move rules: **a non-empty house or crate never into the shed or closet**, and no non-empty crate into a crate, `0x20`; **a crate holds one non-empty house**, `0x27`; **no house holding a placed crate into a crate**, `0x51`; as seen on Live, where a house with items goes to inventory but not the shed): a transaction, then `0x1baf` (removed) or the updated entry, and **`0x2a9e`** (the world object removed).

**World objects (`0x1045` add or update, `0x2a9e` remove, `0x2523` the item being placed moved; the last two carry the 44-byte item reference of the requests' common header)**, the placement object's fields from their sources (`+0x99` is Live's `bDisablePlacementRotation` and `+0x9a` its `bDisableFreePlacement`, the two locks): **model name** = `IT` + the ornament's idfile if the copy has one, else the item's `idfile`, + `_ACTORDEF`, uppercase (the actor lookup is case-sensitive), or on the begin placement object of an NPC item the NPC's race tag (RoF2 previews an NPC item being placed by spawning the race its first three characters name, `0x504b60`; Live sends the item's own `IT63` here, which its newer client doesn't need, and RoF2 would read as race "IT6"); NPC flag and size; the item id (`+0x0c`, Live's RecordNum; RoF2 reads it and never uses it); **the GUID** (the row's, S4); property and record ids; **scale, heading, pitch, roll, position** (note: the entry's order is heading, pitch, roll, scale, position); **ignore collisions** (`+0x98`: an NPC item, or the item's `placeable_ignore_collisions`) and the allowed sub-modes (from the free-placement and rotation flags); **surface type = `placement_type`** (1 = wall: the weapons and shields); **minimum, maximum and default scale**; heading offset = the default heading; **the two wall-mount tilts = the default pitch and roll, plus Live's correction for held items, from the placed copy's effective slots (the item's ANDed with every augment's): pitch +128 when they include a hand (primary, secondary or range), roll +256 when they include secondary but not primary** (shields, torches, held orbs), with no wrapping; **light type = `items.light`**. Every one of these is Live's: on 13,723 captured objects Live's own fields (`DefaultScale`, `DefaultHeading`, `DefaultAngle`, `DefaultRoll`, `PlacementType`, the scale range and locks, `LightType`) hold exactly these values. The server supplies the correction, as Live's server does: RoF2's reader (`0x505400`) copies the tilts verbatim, and only the wall-mount code (`0x557070`) reads them, choosing one by the model's footprint; Live's client never derives them from the item (its only reads of the item's default pitch and roll load or copy item definitions), and its wall-mount code (`0x1402cce30`, tilt choice `0x14026a1d0`) matches RoF2's step for step, so the same values mount the same way. **World objects don't survive zoning**: zone-in sends them all again (chunk 4). **A placed NPC item gets no world object**: its spawn stands for it (Live: 54,509 bound spawns, none with an object).

**NPC items** (vendors, bankers, familiars): **a server NPC** of the item's type (`real_estate_npc_items`: item id to NPC type, content) spawned at the transform and **bound to its entry through the spawn's own fields** (its property id, record id and GUID in RoF2's spawn, T28; `0x21ea` goes only to a player editing the item when its NPC respawns meanwhile, binding the new spawn to the placement); the menu carries its spawn id (`+0x2fc`); merchants and bankers then work through EQEmu's own paths. If one is killed it returns after the item's `npc_respawn_interval`, **in seconds** (owner's decision): 750 for the guild services, 4500 for pets and mounts (the regeneration pool's 38 belongs to an interactive object, not an NPC item). **A familiar that rides a mount is two spawns** (Emperor Ganak's, race 606 on race 625): the familiar, bound to its entry, and its mount (\<familiar\>`s Mount), with no property binding, so the mount has no menu; Peridot spawns both at the transform and binds only the rider (`mount_npc_type_id`; how RoF2 seats the rider is NPC-22). Housing NPC items, rider and mount, stay out of EQEmu's shutdown state saving (T29). **The zone spawns the NPC items of the properties shown in it** once housing is up after boot (the outdoor properties hosted here; an interior's copy adds its house's with step 5, INT-20), and on each placement; a pick-up, storage or mail despawns the item's NPC. **A pet's actions** (type 9, `b` and label Live's code, from `real_estate_npc_item_actions`) go to anyone, as on Live, and act on the spawn: Stay stops it, Walk Around and Run Around roam it about its placed spot at walk or run speed, Follow Me makes it follow the player, Play Dead and Sit Down set its appearance, Kick the Gnome plays the player's kick and sends the gnome running off; **a training dummy's** (Live's four submenus and Report Statistics) change its body type, armor class (5% or 10% of its type's), level (1, 5 or 10, within 1-255) and hit points (1, 10, 100 or 1000 times its type's), on the spawn only, so a respawn restores the type's, and report the four; they come to the owning guild's members and, elsewhere, with Interact Item (Transact's gate; Live offered them to no visitor). What each action does on Live is not captured (NPC-20, NPC-21).

### Permissions: one evaluator for every check

**The server's check follows the client's evaluator (`0x4ff570`)**, so the client's disabled buttons and the server's refusals agree: House of Thule for every real-estate permission (Veil of Alaris and membership feature 10 under a guild plot); **the owner of a player plot passes, and so does the guild's rank 1 (Leader) on its guild plot**; anyone else gets **the most permissive group among their matching entries** in the property's access list (a house or crate uses its plot's): their name's entry, `_Fellowship` if their fellowship is the owner's, `_Guild<rank>` if they're in the owning guild; with no match, Everyone (group 0), since a matching entry's group replaces Everyone rather than adding to it (Live). Live's lists hold no deny (a name or club is assigned Visitor to Co-Owner, groups 1-5), so the most permissive match is the highest group; an explicit deny would beat it (owner's decision). **The group's mask decides** (the second u32 of each pair). ### S7, purchase, sell and transfer

- **Purchase (`0x45be`)**: a vacant Plot or Guild Plot, the player in its zone instance; the price and upkeep option keys within their cost elements (**option keys are indexes**, below); funds in every currency of the price; the client's gate (House of Thule; for a guild plot Veil of Alaris, membership feature 10, `GUILD_ACTION_REAL_ESTATE_GUILD_PLOT_BUY` and `Housing:GuildPlotMinimumMembers`, eqstr 5426); in a guild village, members only; `Housing:MaxPlotsPerCharacter` (eqstr 728, "You can not purchase more than 3 plots.") and `Housing:MaxGuildPlotsPerGuild` (eqstr 750). In a transaction: the currencies taken, owner or guild set, the upkeep option, **`upkeep_expired_time` 0** (an empty escrow doesn't expire a plot; only a charge finding it empty does), `upkeep_settled_at` now and **the first charge one interval later** (D4), and the default access list (S9); then `0x45be` success (the client opens Manage), the record, list A, and the events.
- **Sell (`0x792c`)**: the owner, or `_SELL` for a guild plot, and the client's sell gate (`0x66bf` codes 3, 4, 5, 6 and 10, then the confirmation, eqstr 7634); an expired plot's sale isn't refused. **The plot's placed moving crate is packed with everything on the plot** and goes to the seller's inventory, No Trade while it carries the property (list B, the crate naming the property in its custom data), or is archived until a zone-in with room (list C); a plot with items and no placed crate with room for them is refused at once (eqstr 5276). **The whole escrow is withdrawn to the seller**, floored to copper, with nothing settled first and nothing printed when it's 0; the price isn't refunded; the plot is vacated.
- **Transfer (`0x507f`)**: the owner targets the recipient (with no target the client prints eqstr 3278, "You must first target a living Player Character."), so the recipient is in the owner's zone, and the owner stands on the plot. ### S8, escrow and upkeep (`0x2aa6`)

- **Types:** 0 deposit from the cursor (a failed deposit is refunded: type 0, flag 0); 1 withdraw an amount and 7 withdraw all (permission 2; coin pays out as type 1, flag 1); 2 set the upkeep option (reply type 2); **3 / 4 add a day / week for all items, 5 / 6 for one item** (argument: its upkeep cost id). The client keeps no per-item paid time and computes time left from the balances, so **types 3-6 deposit the equivalent amount into escrow**: the same state, no per-item timers.
- **Option keys are indexes** (`0x7fb970` indexes the options by the key it's given): each cost's keys are 0, 1, 2, ... in order. **A placed item's upkeep is option 0 of its upkeep cost element; the plot's is the option its record selects** (`+0x3c`).
- **A plot's daily upkeep is its definition's upkeep cost** (D13: Live's cost table, 10% of the price per tier); **world charges each plot at `Housing:UpkeepPercent` as its host zone's ruleset sets it** (EQEmu's `zone.ruleset`, the default ruleset otherwise), the value that zone shows. Placed items pay their upkeep ids.
- **Everything placed under the plot draws on its escrow:** the yard's items and everything placed inside its houses, **pets included**, each at its upkeep id (Live, the owner's check).
- **Reductions never pay out** (owner's rule): each currency's net daily cost is **clamped at 0** before charging, so a reduction lowers what is charged but never adds to escrow. The client computes the Manage window's daily cost itself, so it shows 0c at the lowest only if what the server sends never nets below zero; the only reductions are special houses' (`serverWork.md` S13), whose rules keep that true.
- **Each property is charged on its own clock (D4)**: when its `next_upkeep_at` comes, world charges the plot's daily total at that moment (its own upkeep and every placed item's under it), per currency and net of reductions, times the whole seconds since `upkeep_settled_at` over 86,400; then `upkeep_settled_at` is now and `next_upkeep_at` one interval later. Balances are therefore fractional (the schema keeps them exact; the client shows f64). Only placed items cost upkeep, not items in the shed or closet, and a placement settles nothing (the next charge or deposit takes the new total over the whole time since the last one). **A charge the escrow can't cover takes what's left and expires nothing; the next charge, finding the escrow empty, stamps** the property's `upkeep_expired_time` and the `upkeep_expired_at` of every placed item with an upkeep id with its own second, and stores the stamped items but houses (crates too: entry update, `0x2a9e`; a player editing one gets `0x1baf`, which ends the edit cleanly), leaving houses placed but stamped; it mails the owner Live's notice ("Escrow expired on personal plot - First Notice", its body the two lines below) and prints to an online owner "Your player plot at <neighborhood>, <address>'s escrow has expired!" and "Plots will pack up all items, send them to the owner, and become available for purchase again if its escrow has been expired for 90 days." (Live's server composes both; mail dates in Los Angeles wall time are polish). While stamped, nothing can be placed on the plot (`0x18` / `0x19`) and its houses are locked (`0x1920`). Upkeep pauses under a dormant X3 root.
- **Deposits are open to anyone**: this client's permission list has no deposit permission (Live's 2010 list did), and a deposit only helps the owner.
- **A deposit credits, then settles**: the deposit is added, then the time since the last charge or deposit is charged at the current daily total, so on an empty escrow that time comes out of the deposit (Live: 1 pp into a plot expired 1,782 s earlier at 2 pp 1 gp a day left 956.6875 copper, UPK-8); the stamps on the property, its placed houses and its placed items clear (stored items keep theirs); it doesn't move the next charge (owner's decision). Add Day and Add Week deposit the same way from the clicker's purse.
- **Reclaim** (D7): `Housing:UnpaidUpkeepEvictionDays` (90) after a charge stamped a player or guild plot, world reclaims it: everything on it goes into a **Crate of Eviction** (definition 31, filled whatever its caps) for the owner, and the plot is released; the price isn't refunded. The crate is **an archived property the character owns** (list C, which the client shows them) and **becomes a crate item at their next zone-in** (chunk 4). EQEmu parcels can't carry it: they keep an item's id, augments and quantity but not its custom data, which links a crate to its contents. **A deleted owner's expired plot is reclaimed at its next charge**, its items lost (Live reclaimed one within about 30 hours of the deletion, its placed item reaching nobody). An expired house on a paid plot is never reclaimed; it stays locked. **An item carrying a property (a house holding items, a packed crate) is No Trade and No Drop for as long as it carries it**, per instance, which also bars parcels and the bazaar; picked up empty, a house's property is deleted and the item is plain again (Live).

### S9, access (`0x3146`, `0x485d`, `0x3968`)

The client sends a property's whole list (every 3 s while it's being edited). The server checks **may edit** (GM, owner, or Manage) and **the client's grid rule** (a viewer only edits groups below their own), validates the names (existing characters, or the club keys, each in a group from 1 Visitor to 5 Co-Owner, as Live's lists allow), replaces the list in a transaction, sends `0x485d` to everyone who knows the property, and raises the access event; **a player inside an interior who loses Enter is moved out, with no message, to the property's exit point** (S10). **Lists at purchase are Live's defaults** (rules, chunk 1): a plot's masks 3, 3, 2051, 3587, 8071, 8191 and 0 (`0x3`, `0x3`, `0x803`, `0xe03`, `0x1f87`, `0x1fff`, 0) from Everyone to Owner, with no names; a guild plot's 0, 3, 2051, 3587, 8071, 8071 and 0, with `_Guild2` in group 5, `_Guild3` in 4, `_Guild4` to `_Guild6` in 3, `_Guild7` and `_Guild8` in 2. **Neighborhoods and guild halls carry lists of their own** (a public neighborhood's and a hall's are the plot defaults); a house or crate has none and uses its plot's.

### Live's behavior (checked)

Against the official House of Thule housing guide (everquest.com, 2010-10-13, "House of Thule Housing How To") and the fan wikis (Allakhazam's "Player Housing in EverQuest", Fanra's "Player housing"):
- **Neighborhoods create themselves:** each holds 71 player plots and 4 guild plots; as one fills, a new one spawns with a unique name; an empty one is shut down. **Here (D11): random neighborhoods always exist and grow with occupancy; none is pruned**, since Live keeps its empty ones (16 on Vox still listed and empty after 16 days). They're made from the neighborhood definitions `Housing:RandomNeighborhoodDefinitions` lists (`2`, Sunrise Hills alone, as on Live; a custom map joins by adding its definition, X2), each new one picking a listed definition at random (listing one twice doubles its chance). World balances them at boot and on every plot ownership change (those events already pass through world, D2), creating neighborhoods until three things hold: **at least `Housing:MinimumRandomNeighborhoods` (10) in all**; **for each listed definition, at least `Housing:MinimumVacantNeighborhoodsPerDefinition` (1) of its neighborhoods with a free player plot**, so a popular layout always has room; and **the owned share of the player plots across all random neighborhoods under `Housing:NeighborhoodGrowthOccupancyPercent` (30)** (player plots only; guild plots don't count), so neighborhoods can stay sparse while demand still grows them. For the first and third it picks a definition at random; for the second, the definition short of vacancy. Guild neighborhoods count toward none of the three. A new neighborhood is its properties (the neighborhood, its player and guild plots, their regions; Sunrise Hills: 71 and 4), hosted in copies of its definition's template zone started on entry, as interiors are (D3). A list naming anything but neighborhood definitions, or a rule value out of range, is refused loudly: nothing is created until it's fixed. **Names are generated as Live's were:** an optional tree, an optional middle word and a place word, with at least one of the first two ("Maple Bridge Point", "Walnut Lake", "Circle Hills"), from `real_estate_neighborhood_words` (`content/neighborhoodWords.json`: every public name seen in Live's neighborhood search, 10 trees, 5 middle words, 15 place words: 975 names), skipping names in use; once every name is taken, creation fails loudly. **Neighborhood names are unique, enforced in code** (a property's name can't be unique in the schema, since plot addresses repeat in every neighborhood).
- **Guild villages:** an item (the Guild Writ of the Sunrise) created a neighborhood belonging to a guild, listed as "<guild> Village", where **only members may buy plots**; a guild may have several villages but **one guild hall across all of them**. Here: a village is a neighborhood property with the guild's id, created by that item or the GM command, announced with `0x1d3c`; purchases there check membership; a guild hall placement checks the guild has none elsewhere. **Its name is "<guild> Village", with II, III and so on when the name is taken** (Live renumbers on collisions: "The Templar Village II" is its guild's only village, likely from a server merge). **A village whose guild no longer exists keeps its name and acts as a public neighborhood** (Live's search shows it with no guild and other guilds' plots in it, while villages with a guild show only their own guild plot): the server derives it (`activeGuildId`, the guild if it still exists), so records send -1 for its guild and purchases follow the public rules; nothing reacts to a guild's deletion.
- **Limits:** three plots per character, as on Live (`Housing:MaxPlotsPerCharacter`, default 3); **one guild plot per guild** across all neighborhoods (`Housing:MaxGuildPlotsPerGuild`, default 1; Allakhazam's housing page: a guild can own only one guild plot across all neighborhoods); **one house per plot**, the plot definition's `max_children` (1 as on Live; per plot, since the client counts against the yard's own definition), and one crate per plot (the client's rule).
- **Removing a NO DROP item needs its owner, the placer, and a LORE item can't be taken by someone holding one** (the client's rules, replayed in chunk 5).
- **Default access** for a new plot or guild plot: Live's lists (S9).
- **Trophies:** four active personal trophy effects, extendable by AAs (chunk 7).

## Chunk 7: houses and interiors, the crate and layouts, polls, trophies (S10-S12)

### S10, houses and interiors (and X1)

- **A placed house or guild hall is a child property** of its plot (its item's `real_estate_definition_id`; type 3 or 2). **Its interior is a copy of its definition's template** (`dz_id`, `real_estate_zone_templates`: zone, version and zone-in point), started on entry and discarded once empty (D3); the houses share six templates (23000-23005, five definitions each), each guild hall has its own (35633, 35634, 35635, 35642), and the special houses one each (23015-23021, one definition each). An X1 private zone is the same thing with a different template: its definition names, say, the Plane of Hate at a housing version that has no spawns, doors or zone lines.
- **The interior zones** (the client's zone table, `robustness.md`): 714-719 `phinterior3a1`, `1a1`, `3a2`, `3a3`, `1a2`, `1a3`; 720 `phinterior1b1` (a dragon house), 723 `phinterior1d1` (Hermit's Hideaway's, a special house sold on Live); 739-744 `plhogrinteriors*` (ogre, mesh `ter_ogrehouse`) and 745-750 `plhdkeinteriors*` (dark elf, `OBJ_darkelf_door`; a1-a3 finishes like the standard houses), one- and three-bedroom; 766 `phinteriortree` (Evantil's Abode, Rain of Fear's Collector's Edition house, never sold otherwise; its exterior is very likely `IT23651`, packed unplaced in its interior's archive, in the neighborhood's asset list, and tree-sized). **All 15 of these become houses, last** (`serverWork.md` S13). **The `1b1` dragon, ogre and dark elf interiors have no trace on Live** (no item, achievement or mention; emulator zone lists carry only their ids and names): finished, loadable art that apparently never shipped; guild halls 737 `guildhalllrg`, 738 `guildhallsml`, 751 `guildhall3` (721 and 722 aren't zones in this client). **Verified both ways:** every id and name above matches the client's zone table (all 272 registrations in `0x7e0de0`, calls to `0x7dc430` with the id, short name and long name; 767 `interiorwalltest` is a developer test zone), and **PEQ has none of them, nor any of their doors or zone points** (EQEmu's `guildhall`, 345, is the older Guild Hall, a different zone); `sql/housingZones.sql` adds the rows and safe points, leaving each front door (content). **Mapping:** the Monel / Zimel definitions (three rooms: 5-17, and the Manors 32-34) to `phinterior3a*`, the Cobbler / Behroe definitions (one room: 18-29) to `phinterior1a*`, the three interior finishes to a1 / a2 / a3.
- **Entering** (the menu's Enter, menu type 1 on `0x218c`, or a left click on the house's door; a left click on the rest of the house does nothing): Enter permission (1) and the house's and plot's upkeep current (`0x1920` otherwise), then the player joins the interior's running copy, or a new one (D3), at its template's zone-in point. The house itself is no door: it's a world object (`0x1045`) the client draws from the item's model, and its click reaches housing through the real-estate messages, never `OP_ClickDoor`. **The client tells the door from the body itself** (INT-19): a left click sends `0x218c` `{property, record, 0}` only when it lands on the quad the model's `.pts` points POINT1-POINT4 draw on its front (`0x5384d0`), so that is the door click, and housing enters on it under the same checks as the menu's Enter; a click elsewhere on the house sends `0x050c` (within 20 units) or nothing, and does nothing. Models without those points never send it (INT-24). Inside, the house is the current property with no regions, so every placement counts for it (chunk 4), and nothing bounds a placement's position there (chunk 5).
- **Leaving by the front door** puts the player at **the plot's exit point**, in its neighborhood's running copy or a new one, as on Live: a fixed point per plot, not by the house (from 101 Market Street's hut Live put a leaving player 140 units from it, at the same point three times), kept in the plot's definition (`exit_zone_id`, `exit_zone_version`, `exit_x/y/z`, `exit_heading`), so plots can share one point or each have their own (owner's decision). Live's two measured exits each lie at a corner of the plot's outline, so a plot without a measured exit leaves at its outline's first corner (`tools/makeHousingCatalogSql.py`). **T21** (`zone/doors.cpp`, `Doors::HandleClick`): an interior's front door (type 161) is handed to the housing module, which sends the player there; right-clicking it opens the plot's Manage window client-side.
- **`/leaverealestate` (`0x1da9`, a bare request whose four body bytes are stale and ignored):** in a house or guild hall, standard or X1, the same as the front door (on Live, the way out for someone trapped by furniture); anywhere else, only the message "You aren't currently standing in a house or guild hall." (eqstr 6866), as Live answers.
- **Moving a house:** picked up holding items, a house returns to inventory carrying its property, No Trade and No Drop while it does (list B, by the property id in its custom data), its interior and closet intact (on Live, a Palatial Guild Hall picked up kept its property id and its 100 items, and while held its parent was 0, its primary owner the character holding it, and its items' owner names empty); placed on another plot, the property is re-parented. Picked up empty, a house's property is deleted and the item is plain again (Live). **Swap (`0x21ba`):** the message names both houses (the placed one the client chose, `0x5b3170`, and the stored one), so with more than one house on a yard the server swaps exactly the named pair, after checking the named placed house stands on the player's current yard and the stored one is theirs to place; the stored house takes the placed one's transform and the placed one is stored, with the client's failure codes (`0x1228` 48, 49 and 50 when the incoming house lacks room for the outgoing one's real estate items, other items or NPC items, 53 when no house is placed on the player's yard, 55 when the incoming house is placed, 59 when the outgoing house holds a placed crate); the outgoing house's items go into the incoming house's storage (eqstr 5337). A stored house stands in no yard, so players inside the house being stored leave by the yard's exit point, as after Move to Storage. The menu offers Swap Houses (type `0x11`, eqstr 5336) on a stored house in a yard with a placed one (MNU-11).
- **The crate:** a placed crate is a child property of its plot (one per plot, the client's rule). **Store All (`0x6917`)** stores every storable placed item at the player's location (the yard or the house), never a house; **Pack (`0x613d`)** fills the active crate with what fits from the location, stacking like items into one entry, and **Unpack** returns its items to the location as stored items; each applies the individual move rules item by item, and none sends a message (Live). The client holds a request latch after each until a `0x1228` result (or 5 s): the server answers 0, 11 when nothing moved, 22 without a placed crate. `0x613d`'s byte is 1 for Pack and 0 for Unpack (INT-8; the client writes it).
- **Layouts (`0x5b41`):** the client saves layouts itself, as local XML files (`.\%s\%s_%d.xml`, root `RE_Layout` with `Version`, `FileName`, `TypeFlags` and `SaveTime`, one `RealEstateItem` per item with `Name`, `TransformationMold`, `ImageNum`, `Tag`, `NpcItem`, `Type`, `Heading`, `Pitch`, `Roll` and `Scale`), so the server stores none and only ever sees a load; each record is validated with the individual placement or move rules (chunk 5), through the same code as a single commit or move, and applied; the client plans the layout and sends world transforms. A placed record must lie in its destination unless that is a house, which has no regions; one `0x1228` ends the load, 0 when every record applied, else the first refused record's code (INT-29). **Each plot definition's layout origin and heading are Live's switch** (`switch_x/y/z`, `switch_heading`, sent y first), so saved layouts carry between plots.
- **Anchors are placed anchor items** (Lore, one of a kind per character, placed or held; Live): the Primary Anchor (52584), the Secondary Anchor (52585) and a guild's Guild Hall Anchor (50874), found in `real_estate_items`, with no table of their own. Upstream EQEmu has `SE_TeleporttoAnchor` (437) and `SE_TranslocatetoAnchor` (438) only as commented-out defines; **T22** (`common/spdat.h`, `zone/spell_effects.cpp`) defines them and hands them to the housing module with the effect's value, which names the anchor item. **437**: a self gate (Primary Anchor Gate 27749 to the caster's 52584, Secondary Anchor Gate 27753 to their 52585, both 7 seconds) moves the caster at once; an AE cast (Teleport Guild Hall Anchor 33099 to the caster's guild's 50874, everyone within 150, after 20 seconds; target type 40, EQEmu's `ST_AEBard`) sends each target, the caster included, the anchor dialog (`0x7bb1`: the caster's name, the anchor's property and record id, guild id -1, the property's name; RoF2 picks 5329 for the caster when the property is no plot of theirs, which reproduces Live's prompt for a Guild Hall Anchor) and moves them on Yes, the client echoing the offer within its 30 s. **438** (Translocate: Primary Anchor, 27750, a single target within 100 after 10 seconds) sends the target the offer to their own 52584 and moves them on acceptance. Each lands at the anchor's position, 3.5 above it (Live 2.9 to 3.8), facing as before (INT-23); a guild with several Guild Hall Anchors uses the first placed (INT-21). An expired house refuses (`0x14e4`, `0x14e7`, `0x154a`).

### S11, polls

Live runs no polls, so Peridot runs none by default. **The client asks for the polls with a bare `0x15e2`** (after a UI reload), answered with `0x15e2`, `0x6860`, `0x7497`, `0x52b5` and `0x593a`. Polls are run through `#realestate poll` (create, options and labels, publish, close, archive) or content SQL. **Votes (`0x15a8`)** are validated: the poll open (published, within its dates), the voter allowed, each key one of the poll's options, no more than its tick limit. **May vote / may see (`0x7497`)**: every character with House of Thule may vote and see, unless a poll is limited (property polls to the neighborhood's owners). **Results (`0x3311`)** are counted from the votes, ranked, and published after the close unless the poll says otherwise. **Prompt players**: a poll with the flag opens the vote window (`0x7a4d`) at zone-in for those who haven't voted. **Teleport to a ranked property (`0x499a`)** moves the player to that plot's exit point in its neighborhood's instance. **The voting opt-out (`0x6573`)** sets the plot's `voting_opt_out` for a player with Manage on the plot they stand on; a property vote names the occupied plot the voter stands on and is refused for an opted-out one. A question poll's voters are House of Thule characters, a property poll's those who also own a plot; ties share a rank; the zone looks every 30 s for a poll opening or closing and sends `0x39bb` and the may-vote sets, and `0x7a4d` for a prompting question poll that opened (POL-4). `#realestate poll` changes raise the polls event (D2), and each zone sends the lists again.

### S12, trophies

**The last implementation step, outside the first build**: until then trophy items place as ordinary items with no benefit, the trophy opcodes stay unregistered, the trophy tables unused, the bonuses hook (T24) absent and `tribute.cpp`'s two trophy fields 0.

- **Content:** Peridot's `tributes` holds no trophy benefits (chunk 3). Each trophy id the items name needs a `tributes` row (personal or guild by the item's placeable bits) and `tribute_levels` rows (cost and benefit item per tier); the trophy flag is derived (chunk 3).
- **Personal:** the available benefits are computed as the client computes them (`0x5b1b50`): the character's owned plots and their houses, every placed item there that is a trophy (a placeable bit and a trophy id). **`0x4b65`** requests are validated against that set, the tier and the cost; **at most `Housing:PersonalTrophySlots` active** (4 on Live, of the client's 10 slots). While active, the tier costs are charged from the character's tribute points on the trophy timer (`0x51ae`), which runs in the zone's housing process (**T23**).
- **Guild:** the guild's 4 slots (`0x7dd2`), its available benefits (`0x7db5`, from trophies placed in its guild plot and hall), **the edit lock** (`0x7a41`: one editor at a time, kept in `guild_trophy_tribute_state` so it holds across zones), saves (`0x7c1d`) needing rank permission 25 and the lock, costs from guild favor; **opt-in (`0x2bc`)** from a guild member anywhere (Live; RoF2 enables its checkbox only in a hall-flag zone or on a plot under the guild's guild plot, a client limitation), and no opt-out of another member (RoF2 doesn't bind the button); benefits apply to members who opted in.
- **Applying benefits:** EQEmu declares RoF2's trophy inventory types but gives them no slots (`TROPHY_TRIBUTE_SIZE` 0, "unknown"). **T24** (`zone/bonuses.cpp`) applies the active benefits there; whether a tier arrives as a spell (Live's definitions carry a spell id per tier) or as an item, the way tribute's do, is decided with the trophies.

**T23** (`zone/zone.h`, `zone/zone.cpp`): a housing `Timer` in `Zone::Process()`, like `spawn2_timer`, for the zone's periodic housing work: transfer-offer expiry, NPC item respawns, poll prompts, and, with the trophies, trophy timers and charges.

**Rules added:** `Housing:PersonalTrophySlots` (4).

**Content:** zone rows for the interiors and guild halls, with their safe points; the interior exit doors; the trophy benefits (`tributes`, `tribute_levels`).

**To verify in game:** that each interior zone's files exist and zoning in works with no housing messages first (Q11, `robustness.md`); each interior's safe point and front door.
