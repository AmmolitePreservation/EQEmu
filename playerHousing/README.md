# Player Housing (Real Estate) — RoF2 Client Research

Goal: implement EverQuest player housing server-side on EQEmu for the RoF2 client — purchase land, pay upkeep, and place, move, remove, and store objects.

Approach: derive the wire protocol **statically from the client**. The client's parsers define every server → client struct, and its send code defines every client → server struct. A diagnostic DLL (a `dinput8.dll` proxy with send hooks and a packet-injection harness) stays an optional verification tool for later.

## Critical findings (read before any live test)

These are client behaviors that make the housing UI look broken ("dark" controls, windows that open empty, clicks that do nothing) when a precondition is missing. Each has evidence in the linked file.

1. **Many actions act on where the player is standing, not on what the window shows.** The client tracks three property ids in the real-estate manager, recomputed by a once-per-second tick: `+0x8c` (current property, from server `0x6fd0`), `+0x94` (the property the player is **standing in**, by position, falling back to `+0x8c`), and `+0x98` (the **plot the player is on**, the nearest Plot/Guild Plot ancestor of `+0x94`). **Sell and Transfer** use `+0x94`; **the upkeep combobox, voting opt-out and Vote** use `+0x98`. Only the Purchase button uses the property the Purchase window displays. (`windows/RealEstatePurchaseWnd.md`, *Manager property ids*)
2. **Some enabled states are recomputed every frame.** The Purchase window's `0x74d380` runs every frame while the window is visible. It sets **Manage enabled = the plot you're standing on is occupied** (overriding the fill routine's rule), **Vote enabled = you're on this plot AND it's occupied AND not opted out**, and **Opt-out enabled = may manage voting AND you're on this plot**. A test that shows a window for a plot the character isn't standing on gets these controls dark regardless of what was sent. (*Live enable updater*)
3. **The Place button is decided entirely by the real-estate manager's state**, not by `OP_NewZone`: the manager must resolve a current property (`+0x94`: the plot whose **`0x49df` region** contains the player, matched by definition `+0x1c` and scoped under `0x6fd0`'s current property; otherwise `0x6fd0`'s property itself), the item's definition `+0x5ac` must be nonzero (placeable), and no real-estate request may be pending. (`priorResearch.md`, Open question 1)
4. **A pending-request latch blocks actions for up to 5 seconds.** While manager `+0xa4` is set, the purchase/sell/transfer gates and the can-place check refuse. It clears on the server's reply, or after 5000 ms (tick `0x5b0a10`). The second-switch reply `0x626e` clears it.
5. **Without `0x2698` the Purchase window never fills, and without cost options Purchase stays dark.** The fill aborts silently (stale contents) unless the definitions table exists and has the property's definition. Purchase needs the definition's **purchase** cost element (`definition +0x20`) with at least one option that has **at least one cost item**.
6. **Every real-estate permission requires the character's expansion flags**: House of Thule `0x10000`, and Veil of Alaris `0x20000` for guild plots. The flags come from **`OP_PlayerProfile`'s `expansions` field** (the client parser and EQEmu's RoF2 encoder agree), and **`0x0767` and `0x0e48` can overwrite them later**. **On an era-limited server (Peridot is PoP-era) these bits must be sent anyway, or housing is switched off entirely.** Guild plots also need **membership feature 10** (stock EQEmu already passes) and guild rank permissions **27/28** (buy/sell, granted with `OP_GuildUpdate` action 5). (`windows/RealEstatePurchaseWnd.md`, *Character interface and expansion flags*; `permissions.md`)
7. **The real-estate windows have no show gate.** They always open; every check sits on their controls and actions. "The window opens but everything is dark" is the expected symptom of a missing precondition above, not of a broken client.
8. **The client never marks a property as owned by itself.** After a purchase, the Purchase/Manage states only change when the server sends an updated property record (owner name or guild) that makes the "occupied" and "is owner" checks true.
9. **The Items window re-evaluates its action buttons (including Place) every 500 ms** (all 44 controls decoded; flows in `flows/`), and rebuilds its lists when the player moves between plots, houses or crates (`windows/RealEstateItemsWnd.md`, *Live behavior*). **Layouts are local client XML files**, not server data.
10. **Placement is server-driven end to end** (`placementMode.md`): the server's `0x626e` starts it (with the permission map), **`0x49df` supplies the region volumes and clears the permission map** (usable to revoke mid-placement), and only `0x1228` code 0 finalizes a commit. Player movement never cancels placement; validity follows the item's box against the regions, not the player.
11. **No item is placeable under EQEmu's current RoF2 encoder.** The client treats an item as placeable when `ItemQuaternaryBodyStruct.Placeable` (read with the three bytes after it) is non-zero, and `rof2.cpp` hardcodes `iqbs.Placeable = 0`. Every placement and storage rule fails its first check (`0x24`), so the Place button can never enable until the encoder sets it. **The field is a u32 "placeable in" bitmask**, not a flag: **`0x01` certain open zones, `0x02` guild halls, `0x04` houses, `0x08` yards, `0x80` guild yards** (the item display's "This item is placeable in …", `0x69e740`); the placement rules and the trophy tests read individual bits, so **the server must write the right bits per item** (`windows/RealEstateItemsWnd.md`).
12. **No item has upkeep under EQEmu's current RoF2 encoder.** An item's upkeep cost id is item definition `+0x5c4`, read as the u32 at bytes 21–24 after the Heirloom byte; it must match a cost element in `0x2698`. EQEmu's struct doesn't match the client's layout there and zeroes those bytes (`windows/RealEstateManageWnd.md`, *Upkeep*).
13. **The Neighborhood window's list is empty by default with the stock XML, even when the server sends neighborhoods.** Its six filter checkboxes (Non-Guild, Guild, Full/Open PPlots, Full/Open GPlots) have no `<Checked>` value in `EQUI_RealEstateNeighborhoodWnd.xml` and no code sets them, so all start unchecked; each unchecked box hides a category, and every row falls in one of the unchecked ones. Players must tick boxes before any row appears (`<Checked>true</Checked>` on the six buttons shows everything). In testing, an empty list is not evidence that the server sent nothing (`windows/RealEstateNeighborhoodWnd.md`, chunk 1).
14. **Placed items must be re-sent after every zone-in.** Ordinary placed items are client-side world objects created by `0x1045` (the placement object) and cleared on every zone change; NPC items are the server's own spawns bound by `0x21ea` (a `0x1045` NPC item creates no body). Without them nothing appears in the world (`worldLayer.md`).
15. **Two different transform orders.** The placement object (`0x626e`, `0x711a`, `0x1045`) is scale, heading, pitch, roll, position; the placed-item entry (`0x1cef`) and layouts (`0x5b41`, layout files) are heading, pitch, roll, scale, position. The server must convert between them.
16. **Housing tradeskill containers use `OP_ClickObjectAction` with the placed item's property and record ids** in the two fields EQEmu's RoF2 encoder hardcodes to -1 (`unknown04`/`unknown08`); combine and close don't carry the ids, so the server must remember which container each player opened (`worldLayer.md`, step 4).
17. **Guild plot buy and sell need rank permissions 27 and 28.** The client's rank permission masks (ranks 0–8) start at 0 and are filled by `OP_GuildUpdate` (`0x2958`) action 5 {action 5, `+0x50` rank, `+0x54` permission, `+0x58` value}. **EQEmu 23.8.1 already sends action 5 for every rank 1–8 and permission 1–30 on zone-in** (`Client::SendGuildRanks()` in `zone/guild.cpp`, through `GuildUpdateRanks_Struct`), with values from the **`guild_permissions`** table; so the server work is only granting 27 and 28 there for the ranks that should buy and sell. Confirmed live by the diagnostics plugin: a Leader's mask of `0x7ffffffe` includes both (`permissions.md`). Only GMs bypass it. **Send only ranks 0–8 and permission ids 0–31**: the client writes the rank table without a bounds check (`robustness.md`).
18. **`HandleWorldMessage` has two opcode switches** (union 701 opcodes). Real-estate handling exists in both: 30 opcodes forwarded to the manager from the first switch, plus `0x626e` (reply), `0x7bb1`, and the poll messages in the second. (`COVERAGE.md`, *Foundation fix*)
19. **Trophies: personal available benefits come from the trophies placed in the character's plots** (and their houses), identified by item definition **`+0x5ec`** (the trophy benefit id, ≠ -1) plus the placeable flag. **When correcting the item tail for placeable and upkeep, write `+0x5ec` = -1 for ordinary items**, or every placeable item becomes a trophy. **Trophy benefit definitions** are ordinary tribute definitions with **`OP_TributeInfo`'s `unknown128` = 1** (EQEmu always sends 0). (`trophyTribute.md`)
20. **Access lists: each group's entry is `{u32 group number, u32 permission mask}`, not a 64-bit mask.** The client tests the second u32 (permission bit = permission id 0-12). Sending the mask in the first u32 makes every permission read as denied. The client's default masks per group are in `permissions.md`. (Found while writing the diagnostics plugin's spec.)


**Testing:** [`testingNotes.md`](testingNotes.md) lists client behaviors (with the stock XML) that are easy to mistake for server bugs, per window.

**Terminology.** **NPC item** is the client's own term (for example `0x14a3` "…this NPC item because its NPC was not found in the zone"): a placed item backed by an NPC spawn, such as a vendor or banker. It is unrelated to EQEmu's **NPC type** (`npc_types`), which is the specific NPC definition a spawn is instantiated from (tens of thousands of rows), not a category. An NPC item's spawn is instantiated from some NPC type like any other.

## Client build

- `eqgameRoF2.exe`, PE32, build stamp `May 10 2013 23:30:08` — the standard EQEmu RoF2 target.

## What the client needs to show housing at all

1. **Definitions and costs come from the server, not client files.** At construction, `RealEstateManagerClient` (`0x5b21e0`) tries to load `RealEstateDefs.txt`/`RealEstateDefRel.txt`, `RealEstateCosts.txt`, and `RealEstateItemGroups.txt`. If a file is missing, it logs "Could not open file" to `RealEstateErrors.txt` and continues without crashing. Server opcode **`0x2698`** then rebuilds the definitions table (`0x7f5b60`) and the costs table (`0x7fc6b0`) from the packet stream. The owner's RoF2 install has none of these files, which is consistent with that design. The client never reads the item groups, so no client file is needed for them either. Full spec: [`opcode2698DefinitionsAndCosts.md`](opcode2698DefinitionsAndCosts.md).
2. **UI XML** — `EQUI_RealEstate*.xml` plus the `ctxrealestate*.html` help pages.
3. **Zone context** — the server tells the client which property it is in with `0x6fd0` (sets the manager's current real-estate id and definition type; see [`placedItemsAndProperties.md`](placedItemsAndProperties.md)). The zones involved are `neighborhood` (Sunrise Hills), `guildhallsml`, `guildhalllrg`, `guildhall3`, and the house interiors (`phinterior*`, `plhdkeinteriors*`).
4. **Item flags** (*verified*): an item is placeable when `ItemQuaternaryBodyStruct.Placeable` (with the three bytes after it, read as a u32 "placeable in" bitmask: open zones, guild halls, houses, yards, guild yards) is non-zero, and the placement rules and trophy tests read individual bits; EQEmu's RoF2 encoder hardcodes it to 0 (critical finding 11). The same item tail carries the upkeep cost id and the trophy benefit id (critical findings 12 and 19). The Items window's vault / pet split uses the placeable flag and the pet/NPC item predicate (`0x7b1640`).
5. **The server.** Every piece of state comes from server packets: ownership, prices, upkeep balance and timer, the plot list, and placed item positions.

## Message flow

- `CEverQuest::HandleWorldMessage` at `0x4c3250` switches over **431** wire opcodes. As validation, 210 of them match names in EQEmu's `patch_RoF2.conf`.
- The switch case at `0x4cc1d7` forwards 30 opcodes to **`RealEstateManagerClient::HandleMessage(opcode, buffer, length)` at `0x5b2500`**, which has its own switch. Several of its cases wrap the buffer in a stream reader, so those messages are serialized and variable-length rather than fixed structs.
- There is no opcode obfuscation. The receive stub (`0x7d03b0`) and send stub (`0x7d03c0`) are identity functions that only bump counters.
- Send pattern: `opcode = stub(op)` → written as a u16 into the send buffer at `0xdd00e0`, followed by the payload copy, then `[0xdd25ac]->Send(...)`.
- **None of the real-estate opcodes appear in EQEmu's RoF2 conf.** This is entirely unmapped.

**Completeness (full-binary scan).** Every client send goes through the opcode stub `0x7d03c0`. The 24 functions that touch the connection without calling it are connection management or false function starts, not alternate send paths. The binary has **813 send sites**: 799 with a literal opcode (488 distinct, 302 of them named in EQEmu's conf) and 14 computed. Two independent extraction methods agree on every site: disassembly aligned from function starts, and a majority vote over synchronized backward decodes. None of the 14 computed sites is real-estate code; they are the `0x6411`/`0x6471` flag pair, merchant/item message-object senders, and two variable helpers.

Classifying all 186 opcodes EQEmu doesn't name by call-graph distance to real-estate code turns up **no real-estate send opcodes beyond the table above**. The placement overlay and keybind code lives in the display layer (`0x48a5b0`) and sends nothing itself. `0x4290` and `0x378d` sit among the tribute senders and are probably trophy tribute (not traced).

**Control labels are heuristic.** Each one is the nearest child-control comparison before the send site in a linear walk, so treat it as a lead until the struct is decoded.

Observations:
- Several opcodes are **bidirectional**: `0x2aa6`, `0x2691`, `0x21ec`, `0x58c7`, `0x45be`. `0x58c7` is confirmed as an inspect-item request/response pair; the others are likely request/response pairs too, pending decode.
- `0x2aa6` fires from both the Purchase and Manage upkeep controls. It is likely a general real-estate request carrying a sub-type field.

## Message roles resolved so far

- **`0x711a` (client → server): placement commit.** Sent only by `0x5b1f90`, which is entry `[2]` of the manager's placement callback interface (vtable `0x9d90f0`, installed by the constructor). None of the other 17 entries sends anything. The 96-byte payload is built by `0x5b3fb0`:
  - an 18-byte item identifier at `+0x00`
  - five dwords at `+0x14`–`+0x24`, and a zero at `+0x28`
  - seven floats at `+0x2c`–`+0x44`: four copied from the placement object's `+0x7c`–`+0x88` (rotation and scale, by the look of it) and three computed position values
  - two vec3s at `+0x48` and `+0x54`

  When the placement object's `+0x30` is nonzero, the position is made relative to that spawn: it is looked up via `GetSpawnByID` `0x5996e0` and its `+0x138` field is subtracted. That branch also forces one float vector to zeros and two other floats to 1.0. Spawn `+0x138` is a per-spawn float that the client defaults to 0.1 when zero (`0x5a425e`); subtracting it converts actor position to ground position. **Update:** placed items render as spawns in general. `0x21ea` tags a spawn with a placed item's GUID, and when that item is the one being placed it records the spawn id in the placement state. The owner's NPC-placeable idea (vendors and bankers in guild yards) fits as one case of this rather than the only one. It is still untraced whether the commit's `+0x30` comes from that recorded spawn id. See [`placedItemsAndProperties.md`](placedItemsAndProperties.md). Exact field meanings are to be decoded. Moving an already-placed item most likely reuses this message; not yet confirmed.
- **`0x626e` (client → server): place request, not the commit.** Sent from the Items window (Place, menu type 2) and a world click with an item on the cursor. The 60-byte payload is the common request header (item GUID, inventory location, property id, record id) plus `+0x2c` = 1, `+0x30` = 1 and **`+0x34`/`+0x38` = the screen X/Y** (the globals `0xddf684`/`0xddf688` are the mouse position), which the server echoes as D/E in its begin-placement `0x626e` (`placementMode.md`).
- **Confirmation-dialog responses (client → server).** **Correction:** `0x735480` (Items, secondary vtable `0x9f82d8`) and `0x74c8d0` (Purchase, `0x9f91fc`) are not keybind handlers. They are the windows' **dialog-callback interfaces** (window `+0x220`). Their ids `0x64`–`0x69` are the confirmation dialogs those windows open through `[0xf74338]->0x71eb20(target, dialogID, text, flags, timeoutMs, data, …)`, and dialog ids are scoped per target. The mapping and texts are in *Confirmation dialogs* below.
- **`0x507f` (client → server): transfer plot.** Sent when the "transfer your plot to %1?" dialog is confirmed (Purchase dialog `0x65`; the Manage window has the same dialog). The 188-byte struct carries manager `+0x94` and the 64-character name from `[0xdd2648]+0xa4` (the recipient). The recipient gets `0x5a63` and answers with `0x5a63`.
- **`0x6fd0` (server → client): current property.** It deserializes a property record (class vtable `0xa1052c`, reader `0x7fdf00`), stores its id in manager `+0x8c` (the current real-estate id; -1 means none), looks up the definition type into `+0x90`, and hands the record to manager vtable slot `+0x24`. `0x4f09` and `0x63fd` carry the same record class. Record wire order:
  - u32 ×6 (the id is the first, and the 4th is the definition id)
  - string, then string
  - u32, then a u32 count, then a string, then count × u32
  - a u8 count, then count × `{u32 key, f64 value}`
  - u32, u32, u8
- **Manager state reset:** `0x5b1cf0` sets the current id and related fields back to -1 and 10.

**`0x7bb1`: real-estate anchor teleport (both directions).** Houses and guild halls hold teleport anchors.
- **Server -> client (offer):** a 0x54-byte struct (reader `0x4d5cb0`, initializer `0x4b3910`): `+0x00` char[64] **the caster's name**, `+0x40` u32 (0), **`+0x44` u32 the anchor's property id**, `+0x48` / `+0x4c` u32 (-1), **`+0x50` u32 a guild id (-1 = a player anchor)**, then a **string** (the location name shown in the prompt). The client picks the prompt by who cast it (your name vs another) and whose anchor it is: player anchors `0x14cf` / `0x14d1` / `0x14d0` / `0x14ce` ("Are you sure you wish to transport yourself to your real estate anchor in %1?", "Do you wish to be transported by %1 to …"); guild anchors `0x1544` / `0x1546` / `0x1545` / `0x1543` ("…your guild %1's anchor?"). It opens game dialog **`0x8a`** (30 s).
- **Client -> server (accept):** on yes, the game-wide dialog handler (`0x52d540`, dialog-id table `0x52ec10`) sends **`0x7bb1` with the same 0x54-byte struct** (0x56 bytes in total). On no, nothing is sent; the client prints `0x14cd` "You declined the request to be transported to the real estate anchor."

**Game-wide dialogs** (`[0xe67ccc]+8` -> `0x52d540`, ids `0x64`–`0x90` through table `0x52ec10`) that are real-estate related: `0x89` (transfer offer -> `0x5a63`), **`0x8a` (anchor teleport -> `0x7bb1`)**, **`0x8b` (vote-results winner teleport -> `0x499a`, Q24)**. (`0x88` is the account kick -> `0x40e5`, not real estate.)

**Polls** (`polls.md`): server `0x15e2` / `0x39bb` (polls), `0x3311` (results), `0x6860` (option labels), `0x7497` (may vote / may see), `0x52b5` (your votes), `0x593a` (available), `0x7a4d` (open on a poll); client `0x15a8` (vote), `0x499a` (teleport to a ranked property). **Property polls** are voted from the Purchase window's Vote button for the plot the player stands on.

**Guild neighborhoods:** server message **`0x1d3c`** (guild manager `0x425d30` -> `0x425c60`) = {u32 guild id, string `+0x04`, string `+0x44`}: prints `0x14c8` "%1 has created a new neighborhood for your guild's exclusive use! Plots in %2 may only be…" to the guild. Guild plots also need **rank permissions 27/28**, granted with **`OP_GuildUpdate` action 5** (`permissions.md`).

**Commands:** `/realestate <items|manage|trophies|plot>` toggles the housing windows; **`/leaverealestate`** sends **`0x1da9`** (a bare request the server must handle). Key bindings 429–447 cover the windows, help, placement modes, rotation and scale, leave, and vote results (`commandsAndKeybindings.md`).

## Scanner: shared send tails (fixed)

The first inventory read only the opcode pushed immediately before each send-stub call. When the compiler shares one send tail between several branches (each pushes its own opcode and then jumps to the common call), only the fall-through branch's opcode was seen. `realEstateOpcodeScan.py` now handles this:

1. For each stub call, find its basic block (after the last unconditional `jmp`/`ret`) and the block's anchor: its last push, or the block start if there is no push.
2. Find every verified `jmp`/`jcc` in `.text` that lands inside the block after the anchor, and take the opcode pushed before each such jump, following predecessors up to three levels back.
3. To reject bytes that only look like jumps, a jump counts only if at least three synchronized decodes land on it as an instruction boundary.
4. Tails are chosen by majority vote over anchors (not whole tails, whose length varies with where each decode starts). The scan fails loudly on a tie.

Validated on the known case: call `0x73ebea` yields `0x050c` (fall-through), `0x51e3` (via `0x73ed42`), and `0x64a3` (via `0x73ed83`).

**Result:** 813 send calls, **510 distinct literal opcodes** (previously 488), **21 calls reached by more than one opcode**, and 14 calls with only computed opcodes. The full inventory is in [`sendInventory.json`](sendInventory.json), which maps each call address to its `[opcode, via]` pairs. Of the **22 newly revealed opcodes**, **only `0x51e3` and `0x64a3` are real-estate** (Items window interaction menu).

Most of the rest come from ordinary gameplay code (sense traps, mend, forage, pick lock and similar, most of them named in EQEmu's conf). Seven come from the game-wide dialog handler `0x52d540`; dialog ids are scoped per target, and the openers of those dialogs are non-real-estate code, with one exception: **`0x1ff4` (dialog `0x87`) has no opener anywhere in this build** (constant, register and generic-helper ids searched), so it is unreachable; not real estate.

Known nit: at call `0x73ebea` the voted tail starts one byte into the block (`0x73ebc0` instead of `0x73ebbf`). The anchor is push-based, so the result is unaffected.
